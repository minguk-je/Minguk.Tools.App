# 프로젝트 설계 — 솔루션과 프로젝트

2026-09-14. 게임 하나에 딸린 것(사진·라벨·모델·영역·스크립트)이 세 군데로 흩어져 있던 것을
**솔루션 / 프로젝트** 두 겹으로 묶는다. 구조·용어·조작은 **Visual Studio 2026** 을 그대로 따른다.

## 왜

지금 게임 하나의 것이 이렇게 흩어져 있다.

| 무엇 | 지금 자리 |
|---|---|
| 사진·라벨·몹 이름·색·영역·모델 | `프로젝트 경로\Datasets\몹\` |
| 프레임 저장 | `프로젝트 경로\captures\` (어느 데이터셋 것인지 모른다) |
| 스크립트·`.mtsproj` | `%AppData%\Minguk.Tools\Scripts\` (다른 드라이브) |

게임을 하나 더 붙이면 저 셋이 각각 갈라져야 하는데 지금은 데이터셋만 갈라진다.

그리고 **한 게임 안에서도 모드마다 몹이 다르다.** 오버워치 사격장은 "일반봇" 한 종인데 6:6 은 상대 영웅
21종이다 — 사격장 모델을 6:6 에 가져가면 한 마리도 못 찾는다. 디아2·메이플 같은 RPG 면 더 심해서
사냥터마다 몹이 통째로 바뀐다. 모델을 하나로 두면 클래스가 수백이 되고, 사냥터 하나 늘 때마다 전체를
다시 학습해야 한다(D-FINE 이면 몇 시간).

속도는 갈림길이 **아니다** — YOLO·D-FINE 은 출력 채널이 `4+몹수` 라 몹이 3종이든 200종이든 추론 시간이
거의 같다. 갈리는 것은 **정확도와 학습 시간**이다.

## 정한 것 (사용자, 2026-09-14)

- 바깥이 **솔루션**(게임 하나), 안이 **프로젝트**(모드·스테이지·런). VS 의 솔루션/프로젝트와 같은 말이다.
- 사진·라벨·몹 이름·모델·영역·스크립트는 **프로젝트마다 제 것**. 프로젝트 폴더 하나에 그 런에 필요한 전부가 들어간다.
- 앱을 **켤 때마다 시작 창**에서 솔루션을 고른다.
- 셸 도구 모음에 **시작 프로젝트** 콤보를 두고, 실행하면 그것이 돈다(VS 2026 의 `▶ 프로젝트이름 ▾`).
- 화면(캡처·라벨링·스크립트)은 **프로젝트마다 따로** 띄울 수 있다. **실행은 하나만.**
- 프로젝트를 고르는 자리는 메뉴창보다 위.

### 프로젝트 단위는 "맵" 이 아니라 "런"

디아2는 블러드무어에서 콜드플레인으로 걸어가면 화면이 안 끊긴다. 맵마다 프로젝트를 나누면 걸어가는 중에
사람이 계속 바꿔 줘야 한다. **한 번 누르면 끝까지 도는 덩어리**가 한 프로젝트다 — 안달리엘런·메피스토런·카우방.

### 사진을 프로젝트마다 두는 이유

한동안 "사진·라벨은 솔루션에 한 벌, 모델만 프로젝트마다" 를 검토했다. 같은 몹이 여러 런에 나오면 두 번
찍게 된다는 걱정이었는데, **사진은 어차피 그 스테이지에서 찍힌다.** 카타콤 좀비와 두랜스 좀비는 같은
몹이라도 배경·조명이 달라 사진이 다르다. 겹치는 것은 `classes.txt` 의 이름 한 줄뿐이다.

그래서 프로젝트마다 제 것으로 두고, "프로젝트를 고르면 전부 교체" 라는 예외 없는 규칙을 얻는다.
나중에 아쉬우면 "다른 프로젝트에서 사진·라벨 가져오기" 를 붙인다 — 미리 만들지 않는다.

## 폴더

```
<프로젝트 경로>\
└─ 디아2\                          ← 솔루션 폴더 (= 게임)
   ├─ 디아2.mtsln
   ├─ 공용\                        ← 공유 프로젝트 (VS 의 .shproj)
   │  ├─ 공용.mtsproj
   │  └─ 포션먹기.csx  쫓기.csx
   ├─ 안달리엘런\                  ← 프로젝트 (= 런)
   │  ├─ 안달리엘런.mtsproj        ← 공용 을 ProjectReference 로 문다
   │  ├─ main.csx  Resources\  bin\
   │  ├─ images\  labels\  classes.txt  class-colors.json
   │  ├─ captures\
   │  ├─ detector.onnx  detector.json  detector.<이름>.onnx
   │  └─ regions.json
   └─ 메피스토런\ …
```

- **프로젝트 폴더가 곧 데이터셋 폴더다.** 지금 `Datasets\몹\` 이 하던 일을 프로젝트 폴더가 그대로 한다 —
  학습·재현율·모델 들이기 코드가 보는 자리만 바뀌고 하는 일은 같다.
- 스크립트(VS 것)와 데이터(우리 것)가 나란히 있다. 데이터는 `bin\`·`Resources\` 처럼 **폴더 규약**으로 두고
  `.mtsproj` 목록에는 **안 넣는다** — 사진 수백 장이 목록에 들어가면 솔루션 탐색기가 못 쓰게 된다.
- 학습 경로(`Vision.TrainingRoot`)는 그대로 바깥이다. 프로젝트가 몇이든 파이썬 환경은 한 벌이다.

## 솔루션 파일 (.mtsln)

```json
{
  "version": 1,
  "name": "디아2",
  "startupProject": "안달리엘런/안달리엘런.mtsproj",
  "projects": [
    { "path": "공용/공용.mtsproj",             "kind": "Shared" },
    { "path": "안달리엘런/안달리엘런.mtsproj", "kind": "Normal" },
    { "path": "메피스토런/메피스토런.mtsproj", "kind": "Normal" }
  ]
}
```

- 경로는 **솔루션 폴더 기준 상대, `/`**. 폴더째 다른 PC 로 옮겨도 그대로 열린다.
- `.sln` 과 같이 **목록만 든다.** 폴더에 프로젝트를 만들어 놓기만 해서는 안 들어간다.
- 없어진 프로젝트는 솔루션 탐색기에 "찾을 수 없음" 으로 남긴다 — 조용히 빼면 사람이 지운 줄 모른다.
- `kind` 는 **이름으로 저장**한다. 값을 늘리기만 하고 순서를 바꿔도 옛 파일의 뜻이 안 변하게.

## 프로젝트 (.mtsproj)

`Input/Scripting/Projects/ScriptProject` 를 **그대로 쓴다.** 늘리는 것은 하나뿐이다.

- `ScriptItemKind.ProjectReference` — 값을 **더하기만** 한다.
- 공유 프로젝트를 물면 그 프로젝트의 `Source` 항목이 **컴파일에 합쳐진다**. VS 의 공유 프로젝트와 같다.
  `CompiledScriptBuilder.Assemble` 이 이미 여러 소스를 한 덩어리로 합치므로 붙일 자리가 있다.

**`../` 링크는 안 쓴다.** 프로젝트 폴더 밖 파일을 막는 규칙(`ScriptProject` 의 "프로젝트 폴더 밖의 파일은
넣을 수 없습니다")은 그대로 둔다 — 폴더째 옮겨도 열리는 성질이 거기서 나온다. 공유는 프로젝트 참조로 한다.

## 시작 창

앱을 켜면 먼저 뜬다(사용자 결정). VS 2026 시작 창과 같은 모양.

```
┌ 최근 솔루션 ────────────┬ ───────────────────────┐
│ 디아2      D:\…\디아2   │  솔루션 열기...        │
│ 오버워치   D:\…\오버워치│  새 솔루션 만들기...   │
└─────────────────────────┴────────────────────────┘
```

- 최근 목록은 `Project.RecentSolutions` (최신 우선, 10개). 없는 폴더는 흐리게 두고 누르면 지울지 묻는다.
- 새로 만들면 `<프로젝트 경로>\<이름>\<이름>.mtsln` 과 첫 프로젝트를 같이 만든다 — 빈 솔루션은 아무것도 못 한다.
- 취소하면 앱을 닫는다. 솔루션 없이 열리는 화면이 없다.

## 셸 — 도구 모음과 시작 프로젝트

`MainView` 맨 위에 `dxb:BarManager` + 도구 모음 한 줄을 넣는다.

```
┌ 제목 ─ 안달리엘런 - 디아2 - Minguk Tools ───────────────┐
├ 도구 모음 ─ [▶ 안달리엘런 ▾] [⏹ 중지] [⏸ 비상 정지] ──┤
├──────────┬──────────────────────────────────────────────┤
│ 📁 디아2 │  탭들                                         │
│──────────│                                               │
│ 화면캡처 │                                               │
│ 라벨링   │                                               │
│ …        │                                               │
└──────────┴──────────────────────────────────────────────┘
```

- `▶ 이름 ▾` 은 **`BarSplitButtonItem` 하나**다(테마 갤러리가 쓰는 그 컨트롤). 누르면 실행, 화살표는 시작 프로젝트 목록.
- 왼쪽 메뉴창 위에는 **솔루션 이름만** 둔다. 누르면 시작 창을 연다.
- 제목 표시줄에도 `<시작 프로젝트> - <솔루션> - Minguk Tools` 로 적는다 — 메뉴창은 접히므로 접어 두면
  지금 어느 프로젝트인지 사라진다. 모델과 스크립트가 통째로 달라지는 값이라 안 보이면 위험하다.
- **중첩 BarManager 주의.** 스크립트 화면이 탭 안에서 제 `BarManager` 를 쓴다. 안쪽 도구 모음·메뉴가 바깥으로
  병합되지 않게 막는다. 안 막으면 스크립트 탭을 열 때 셸 도구 모음에 그쪽 항목이 끼어든다.

**실행을 누르면** 시작 프로젝트의 플레이 화면을 앞으로 가져오고(없으면 열고) 돈다. VS 가 디버그 창을 띄우는 것과 같다.

### 단축키 소유가 여기서 정리된다

지금은 스크립트·플레이·입력 테스트 세 화면이 각자 F5 를 쥐려 해서 **같이 열면 뒤엣것이 등록에 실패한다.**
실행이 셸 것이 되면 **셸이 F5·F6·Pause 를 한 번만 쥔다.**

| 키 | 누가 | 무엇 |
|---|---|---|
| F5 | 셸 | 시작 프로젝트 실행 / 멈춘 곳에서 계속 |
| F6 | 셸 | 중지 |
| Pause | 셸 | 비상 정지 (도는 동안만) |
| F8 | 화면 | 담기. 마지막에 본 캡처·스크립트 화면이 받는다(`HotkeyClaim` 그대로) |
| F10 | 화면 | 한 줄 (스크립트 화면) |

## 화면 넷이 보는 것

| 화면 | 프로젝트의 무엇 |
|---|---|
| 화면캡처 | `images\` 에 담고 `captures\` 에 프레임 저장 |
| 라벨링 | `images\ labels\ classes.txt class-colors.json`, 모델·학습 |
| 스크립트 | 솔루션 **전체** 트리, 편집은 아무 프로젝트나. 몹 찾기는 그 탭의 프로젝트 모델 |
| 플레이 | 그 프로젝트의 `.mtsproj` / `bin\*.mtsx` |

**시작 프로젝트를 바꿔도 이미 열린 탭은 제 프로젝트를 계속 본다.** VS 가 그렇다 — 시작 프로젝트를 바꿔도
열어 둔 파일이 안 닫힌다. 바뀌는 것은 굵게 표시되는 프로젝트와, **새 탭을 열 때의 기본값**이다.

`LabelDataset.ConfiguredRoot`(앱 전체 키 `Vision.DatasetRoot`)는 없어진다 — 자리를 화면이 아니라
**탭이 든 프로젝트**가 정한다.

## 화면을 프로젝트마다 여러 개 띄운다

지금은 **화면당 탭 하나**다. `MainViewModel.DoShowWindow` 가 화면 이름으로 기존 문서를 찾고
`CreateDocumentCore` 가 Id 를 `DocId_<화면이름>` 으로 고정한다.

- Id 에 프로젝트를 넣는다 — `DocId_LabelingView_안달리엘런`. 탭 제목은 `라벨링 (안달리엘런)`.
- 탭을 끌어내면 떠 있는 창이 된다(`DocumentGroup` 기본). VS 의 `창 > 새 창` 과 같다.
- 여는 길 둘: 메뉴 클릭 = **시작 프로젝트**로 열기(있으면 활성화) / 솔루션 탐색기에서 프로젝트 오른쪽 클릭 > `라벨링 열기`.

**고칠 것 넷**

| | 무엇 |
|---|---|
| 설정 키 | `AppSettingUtility` 가 **타입 이름**으로 저장한다. 라벨링 둘이 열리면 확대 배율·열 너비를 서로 덮어쓴다. 키에 프로젝트를 섞는다 — `LabelingViewModel.안달리엘런.LabelZoom` |
| F8 담기 | 두 캡처 화면이 동시에 못 쥔다. `HotkeyClaim` 규칙은 그대로 두되 **어느 프로젝트로 담겼는지 아래 바에 적는다** — F8 을 누를 때 사람은 게임을 보고 있다 |
| 모델 메모리 | 몹 찾기를 켠 화면마다 DirectML 세션이 뜬다. 15MB 모델이라 두셋은 괜찮지만 GTX 1060 3GB 에 무한정은 아니다 |
| 실행 | **동시 실행은 막는다.** 두 런이 같이 돌면 마우스를 서로 뺏는다. 도는 것은 늘 시작 프로젝트 하나 |

보는 화면은 여러 개, **돌리는 것은 하나**다.

캡처는 이미 준비돼 있다 — `SharedCaptureHub` 가 같은 창을 잡는 화면들에 세션 하나를 나눠 준다.

## 학습

프로젝트 폴더가 곧 데이터셋 폴더라 **학습 코드는 그대로다.** `YoloTrainer` 가 `--root <폴더>` 를 넘기고
`yolo-학습.py` 가 `path: <폴더>` / `train: images` / `names: classes.txt` 를 쓰는 것이 그대로 맞는다.
D-FINE 도 같은 자리를 COCO 로 내보낸다.

프로젝트마다 몹이 적으니 학습이 짧아진다 — 카우방처럼 한 종이면 YOLO11n 이 몇 분이다.
다른 프로젝트는 건드리지 않는다.

## 옛 자리에서 옮기기

한 번만 도는 이주. 설정에 솔루션이 없고 옛 키가 있으면 한다.

| 옛 자리 | 새 자리 |
|---|---|
| `Vision.DatasetRoot` 가 가리키던 폴더(`…\Datasets\몹`) | `…\오버워치\사격장\` |
| `…\프로젝트\captures\` | `…\오버워치\사격장\captures\` |
| `%AppData%\Minguk.Tools\Scripts\*` | `…\오버워치\사격장\` |

- 솔루션 "오버워치", 프로젝트 "사격장" 을 만들고 시작 프로젝트로 둔다.
- 시험 폴더 `몹-yolo`·`몹-yolo11s` 는 junction 이라 **옮기지 않는다** — 링크를 먼저 지우고 옮겨야 한다.
- 옮기기 전에 무엇을 어디로 옮기는지 보여 주고 한 번 묻는다. 사진 수백 장은 다시 만들 수 없다.

## 만들 순서

1. **모델·파일** — `Solution`(읽기·쓰기·프로젝트 더하기·빼기), `SolutionWorkspace`(지금 솔루션·시작 프로젝트),
   설정 키. 화면 없이 하네스로 본다.
2. **이주** — 옛 자리를 첫 솔루션으로. 실제 데이터가 걸린 곳이라 먼저 한다.
3. **시작 창** — 최근·열기·새로 만들기. 취소하면 앱 종료.
4. **셸** — `MainView` 도구 모음, `▶ 시작 프로젝트 ▾`, 왼쪽 위 솔루션 이름, 창 제목, 문서 Id 에 프로젝트,
   F5·F6·Pause 를 셸로.
5. **화면 넷 연결** — `LabelDataset.ConfiguredRoot` 를 걷어내고 탭이 든 프로젝트를 본다. 설정 키에 프로젝트 섞기.
6. **공유 프로젝트** — `ProjectReference`, 솔루션 탐색기에 솔루션 뿌리 + 프로젝트들.

## 검증

- `--views` — 화면 생성. 셸 도구 모음이 늘어나므로 여기서 먼저 걸린다.
- `--labeling-screen` · `--script-screen` — 프로젝트를 임시로 하나 만들어 띄운다.
- **새로 `--solution`** — 솔루션 만들기·열기·프로젝트 더하기·시작 프로젝트 바꾸기·공유 프로젝트 소스가
  합쳐지는지·이주. 화면 없이 도는 순수 검사라 `--vision` 처럼 안전하다.

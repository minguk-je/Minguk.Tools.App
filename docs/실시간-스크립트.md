# 실시간 스크립트 · 조준 · 입력 · 디버그

스크립트·플레이 화면의 스크립트는 **실시간 모드**다 - 부르면 곧바로 입력이 나가고 화면을 읽는다.
입력 테스트 화면은 **계획 모드**(적어 두었다 나중에 보냄)다. CLAUDE.md 에서 떼어 온 자세한 규칙과 실측이다.

## API 두 벌

- 계획 `SequenceScriptApi`, 실시간 `Input/Scripting/Live/LiveScriptApi`. 표(`ScriptApiCatalog`)의 `Mode` 가 어느 쪽인지 말하고, `--vision` 이 리플렉션으로 이름을 센다.
- 이름은 영문·한글 둘 다(`Type`/`글자`). 세 언어(C#·Python·JS)가 같은 이름·같은 인자.
- API 를 늘리면 같이 고칠 곳: `LiveScriptApi`/`SequenceScriptApi` · `ScriptApiCatalog` · `JavaScriptEngine.Bind` · 구문 강조 `Resource/SequenceScript.*.xshd`.
- 엔진마다 두 길: `CheckLiveAsync`(컴파일·문법만 - 부작용 없어야 한다) · `RunLiveAsync`(끝까지). 파이썬은 `name = api.name`, JS 는 `function name(){ return api.name.apply(api, arguments); }` 로 심는다.
- 끝난 이유는 `LiveScriptApi.Outcome` 으로 가른다(중지·비상 정지·`끝()` = 빈 목록, 안전장치 = `GuardMessage`) - 예외 타입으로 가르면 파이썬을 거쳐 전부 PythonException 이 된다.
- 검출 자리는 화면 픽셀(`ScriptDetection`). **겨누는 곳은 `머리x`·`머리y`**(사각형 위에서 높이의 22% - 18% 은 사격장 봇에서 조금 높았다, 2026-09-18).
- `LiveScriptSession` 이 스크립트·플레이 화면이 같이 쓰는 묶음(출력 칸·비상 정지·API 에 빌려 줄 것). `ScriptPlayer` 는 한 바퀴를 `ScriptRunContext.RunOnce` 로 받는다.
- 인식 허브 `IPerceptionHub`(`PerceptionHubFactory.Default`, 하네스는 가짜) - 상태·검출·이름표를 올리고 스크립트가 읽는다. 프레임 픽셀은 `읽기()` 를 부른 뒤에만.

## 안전장치 - 전부 `LiveScriptApi` 안

- 대상 창이 앞에 없으면 입력을 안 보내고 멈춘다(SendInput·Interception). **같은 프로세스면 통과**(`ForegroundWindow.IsInFront` - 게임은 IME·오버레이를 앞에 둔다).
- 초당 입력 상한 30, 모든 호출이 중지 토큰을 본다(`쉬기()` 도), 눈이 없으면 `검출들()` 은 빈 목록이 아니라 멈추고 이유를 말한다. 실행 시간 상한 `RunTimeLimitSeconds`(600).
- **비상 정지 Pause** 는 도는 동안만 쥔다(`EmergencyStop`) - 중지 + 누르고 있던 키·버튼 전부 뗌(`ReleaseAll`).
- 실행은 소리로 알린다(`ScriptPlayer.Chime`) - 게임이 앞에 있으면 글자를 못 본다.
- `Click` 은 커서가 대상 창 밖이면 100ms 기다려 보고 그래도 밖이면 안 누른다.

## 메뉴 누르기 - 글자로 찾는다

- **`글자찾기("사격장")`·`글자누르기("사격장")`**(사용자, 2026-09-18 "특정 메뉴를 눌러야 한다"): 화면에서 그 글이 든 낱말·줄을 찾아 자리(`x`·`y` 화면 픽셀, `너비`·`높이`, `글`)를 준다. 없으면 null.
  게임 메뉴는 대개 글자라 라벨링·학습 없이 이것으로 된다. 자리는 `ScriptSpot` - `이동클릭(자리.x, 자리.y)` 에 그대로 넣는다.
- **화면 전체는 6조각(가로 3 × 세로 2, 15% 씩 겹침)으로 나눠 읽는다.** 줄 찾기 모델은 긴 변을 640 으로 줄이므로 1080p 를 통째로 넣으면 30px 글자가 10px 이 되어 못 찾는다.
  조각마다 OCR 한 번이라 **0.3~1.3초**(실측 1.2초) - 매 프레임이 아니라 메뉴가 떴을 때 부른다. `글자찾기("사격장", "메뉴자리")` 처럼 이름 붙인 자리를 주면 그 자리만 읽어 빠르다.
- 띄어쓰기는 무시하고 견준다(OCR 이 「사격 장」 으로 나누기도 한다). 낱말 하나에 다 들어 있으면 그 낱말 자리, 여러 낱말에 걸치면 그 줄 자리. 여러 곳이면 가장 위·왼쪽.
- 검사 `--aim` 의 마지막 세 줄: 1080p 에 메뉴 글자 넷을 그려 「사격장」 을 찾고(그린 자리에서 1px 안) 눌러 본다(가짜 어댑터).

## 그림으로 된 메뉴 - 본보기 대조

- **`그림찾기("사격장.png")`·`그림누르기(...)`·`그림있나(...)`·`그림닮음(...)`**(사용자, 2026-09-18 "사격장 글이 아니고 큰 이미지인데"): 버튼이 글자가 아니라 그림(썸네일 카드·아이콘)이면
  본보기 한 장과 견줘 찾는다. 라벨링·학습은 "화면 어디에 뜰지 모르는 것"(검출)에 쓰고, 그림이 그대로 같은 것은 이쪽이 맞다. OpenCV 는 안 싣는다 - 필요한 것이 이 함수 하나인데 네이티브가 100MB+ 다.
- **영역 이미지 만들기**: 캡처를 켜고 영역 패널에서 `[새 영역]` → 미리보기에서 그 버튼에 맞게 크기를 맞추고 이름을 붙인 뒤 도구 줄의 **`[영역 이미지 저장]`**(`SaveTemplateCommand`, 인식 도구 줄에도 있다).
  프로젝트 `Resources\<영역이름>.png` 로 저장된다(구역을 골랐으면 `<영역>.<구역>.png`). 같은 이름이면 덮어쓴다 - 다시 맞춰 저장하는 일이 잦다.
  카드 **안쪽만**, 움직이는 배경은 되도록 빼고 자른다.
- **정규화 상호상관**(NCC, `TemplateMatch`) - 조각과 본보기에서 각자 평균을 빼고 표준편차로 나눠 곱해 더한다. **밝기·대비가 달라져도** 같은 그림이면 1 에 가깝다
  (실측: 화면이 35% 밝아져도 0.96). 문턱 기본 0.8. 안 눌리면 `그림닮음("사격장.png")` 을 출력해 보고 조절한다.
  **크기가 달라지면 못 찾는다** - 게임 해상도를 바꿨으면 본보기를 다시 만든다.
- **계단 셋으로 찾는다**(1/8 → 1/2 → 원본): 1920x1080 에서 346x216 본보기가 **0.5초**. 곧바로 원본에서 후보 다섯을 훑던 때는 1.8초였다(실측).
  자리 이름을 주면(`그림있나("궁극기준비.png", 0.9, "궁극기자리")`) 그 자리만 봐서 훨씬 빠르다 - 스킬 아이콘·버프 표시처럼 자리가 고정된 것은 이렇게.
- 본보기는 한 번 읽어 회색조로 들고 있는다(스크립트마다). 검사 `--vision` 의 `본보기:` 다섯 줄.
- **마스크 - 다각형 안만 견준다**(사용자, 2026-09-23 "Adorner 안에 폴리곤 식의 구역을 자유롭게 지정해서 이부분만 매칭"): 둥근 아이콘·뒤가 비치는 버튼·안쪽 그림만 바뀌는 카드는
  네모 귀퉁이의 배경이 화면마다 달라 닮음을 깎는다(실측 합성 화면: 마스크 없이 0.59 → 마스크 1.00).
  - 영역 패널 **`[마스크]`**(`AddMaskCommand`) → 고른 구역(영역을 골랐으면 첫 구역)에 가운데 팔각형이 놓이고 그 구역이 골라진다. 노랑 네모(꼭짓점)를 끌어 맞추고,
    변 가운데 동그라미를 끌면 꼭짓점이 늘고, 꼭짓점을 **오른쪽 버튼**으로 누르면 빠진다(셋은 남는다). 다 맞췄으면 `[영역 이미지 저장]` 을 **다시** 누른다. 지우기는 `[마스크 지우기]`.
    점을 찍어 그리는 모드는 두지 않았다 - 미리보기의 빈 곳 누르기가 이미 "새 영역" 이라 같은 누름이 두 뜻이 된다.
  - **좌표는 구역 기준 0~1**(`RegionCell.Mask`, `regions.json` 의 `"mask": [[x, y], ...]`, 없으면 키를 안 적는다) - 구역을 옮기고 늘리고 돌려도 따라간다. 저장되는 그림이 곧 구역을 세운 그림이라서다.
  - **PNG 알파가 마스크다**(`PolygonMask.Apply` - 가장자리는 4x4 로 나눠 반쯤 걸친 픽셀은 반투명). 그래서 `그림누르기("이름.png")` 는 그대로고, 그림판으로 지운 PNG 도 먹힌다.
    읽을 때 `GrayImage.From(..., useAlpha: true)` - **본보기만** 알파를 본다(화면 조각의 캡처 알파는 믿을 값이 아니다). 알파가 모두 255 거나 모두 0 이면 마스크 없음.
  - 대조(`TemplateMatch.ScanMasked`): 본보기·조각 모두 마스크 안 무게만으로 평균·분산을 낸다. 창마다 무게가 달라 적분 영상을 못 써 곱의 합이 셋 - 마스크 없는 것보다 두세 배 느리다(80x80 이 1080p 전체에서 0.2초).
    조각 값에서 128 을 빼고 제곱합을 쌓는다(float 분산이 덜 뭉개진다). 마스크 안이 12px 미만이면 안 찾는다.
  - 글자 읽기는 마스크를 안 본다. 검사 `--template`·`--vision` 의 `마스크:`·`마스크 편집:` 줄(`minguk-region-mask.png` 를 찍는다).

## 미니맵으로 방향 보기 - 방위 · 가기

- **`방위()`·`목표방위()`·`가기(방위, 밀리초)`**(사용자, 2026-09-23 "미니맵으로 방향 보면서 처리가 가능해?"): 게임에 자동 이동이 있어도 **「자동 이동할 수 없는 퀘스트」**가 있다.
  미니맵 한가운데 캐릭터 화살표를 읽어 몸이 어디를 향했는지 알고, 노란 목표 마커의 방위·거리를 읽어 그쪽으로 걷는다. 검출·OCR·본보기 대조는 「화면 어디에 무엇이 있나」를 답하지 **어느 쪽을 보고 있나**는 답하지 못한다.
- **준비는 두 걸음**: ① 영역 패널에서 미니맵을 둘러 **「미니맵」** 이라는 이름의 자리를 만든다 ② 도구 줄의 **`[미니맵 익히기]`** 를 한 번 누른다.
  앱이 색으로 화살표를 뽑아 `Resources\미니맵화살표.png`(조각 원본)와 `minimap.json`(기준각·색 규칙·회전 배율)을 만들고, 화살표가 어느 쪽을 향한 것으로 봤는지 한국어로 알린다.
- **화살표는 캐릭터 몸 방향이지 카메라 방향이 아니다**(실측 2026-09-23: 걸으면 56° 돌고, **마우스만 돌리면 0°**). 카메라 방향은 미니맵에 없다 - 밝은 부채꼴이 후보였으나 한 장에서 둘로 갈라졌고 지도의 통로와 정렬돼 있었다.
  그래도 된다: 알고 싶은 것은 「W 를 누르면 어디로 가나」이고, W 를 누르면 몸이 카메라 쪽으로 돌아 그 답이 된다.
- **`가기` 를 쓰고 `바라보기` 는 아껴 쓴다.** `바라보기` 는 **열린 고리**라(마우스를 돌려도 화살표가 안 돌아 확인할 길이 없다) 정확도가 회전 배율에 달렸다.
  `가기` 는 W 를 누른 채 0.12초마다 미니맵을 보고 어긋난 만큼 고치므로 배율이 좀 틀려도 수렴한다.
- **회전 배율(`회전배율()`, 도/카운트)은 스스로 잰다** - 마우스를 돌리고 **짧게 걸어** 몸을 카메라에 맞춘 뒤 방위가 얼마나 달라졌는지 본다(마우스만으로는 못 잰다).
  벽에 막힌 표본은 버리고 가운뎃값을 써 `minimap.json` 에 적는다. 조준 배율(카운트÷px)과는 **다른 값**이다 - 이쪽은 화면 픽셀을 안 거쳐 카메라 피치·FOV 와 무관하다.
- **각도는 회전 본보기 대조**(`MinimapReader`) - 본보기를 1°씩 360번 돌려 겹침이 가장 큰 각. **±1~2°**, 한 번 0.5ms 라 프레임마다 돌려도 된다.
  무게중심에서 가장 먼 픽셀을 머리로 보는 방법은 **틀린다**(이 아이콘은 꼬리가 머리보다 길다 - 필드 한 장에서는 맞는 듯했으나 던전에서 깨졌다).
- **익히기가 머리를 가리는 규칙**: 방향마다 부챗살(±35°) 안 픽셀의 **중심거리 합**이 가장 무거운 쪽(머리는 짧지만 넓고, 꼬리는 길지만 가늘다). 정확도 ±5~10°.
  머리와 꼬리의 무게가 비슷하면 흔들려(실측 여유 1.05배인 장면에서 20° 어긋남) **여유 배수를 같이 알리고** 낮으면 `출력(방위())` 로 확인하라고 말한다. 다르면 `minimap.json` 의 `headingAtTemplate` 을 고친다.
- 검사 `--minimap`(1초, `--vision` 에도 들어 있다) - 실제 게임 화면 다섯 장으로. 던전 셋은 서로 0°, 걸은 뒤 −56°, 필드 −31°, 마커 105 → 118px.

## 다른 프로젝트로 - 프로젝트실행 · 프로젝트이동

- `프로젝트실행("이름")` - **함수 부르기**. 그 줄에서 기다렸다가 끝나면 다음 줄로 돌아온다(그 안의 `끝()` 은 그 프로젝트만 끝낸다). 도는 동안 검출 모델·이름 붙인 자리·리소스는
  그 프로젝트 것, **돌아오면 부른 쪽 것으로 되돌린다**(`RestoreProjectContextAsync` - 안 되돌려 다음 줄의 `목표()` 가 옆 프로젝트 모델을 본 적이 있다). 스크립트 화면은 소스를, 플레이는 `bin\*.mtsx` 를 돈다.
- `프로젝트이동("이름")` - **넘어가기**(사용자, 2026-09-19). `끝()` 처럼 그 줄에서 끝나고, 실행기 맨 바깥(`ProjectMoveRequest.RunWithMovesAsync`)이 그 프로젝트를 이어 돌린다 -
  쌓이지 않아 메인화면 → 영웅선택 → 사격장 → 다시 메인화면처럼 돌고 도는 흐름도 된다(`프로젝트실행` 으로 이으면 한 겹씩 쌓여 끝없이 돌면 스택이 넘친다).
  `프로젝트실행` 안쪽에서 이동하면 부른 쪽도 끝내고(쌓인 것을 다 걷고) 넘어간다. 요청은 host 한 벌(`LiveScriptHost.Moves`)을 안쪽 host 가 나눠 쓴다.
  검사 `--vision` 의 `프로젝트이동:`·`프로젝트실행:` 줄(깊이가 늘 1겹, 30바퀴).

## 목표 · 조준

- **한 마리를 잡을 때까지 그 검출만 본다**(`목표()`·`목표풀기()`). `가장가까운검출()` 만 쓰면 두 마리 사이를 왕복한다(실측).
  같은 검출은 **보낸 카운트 ÷ 배율만큼 옮겨 놓고** 찾는다. 못 찾으면 400ms 는 null 을 주고 기다린다.
  **새로 고르는 목표가 300px 넘게 멀면 두 번 연속 같은 자리에 보여야** 준다 - 한 프레임짜리 헛것으로 시야가 튀었다(실측).
  **고정한 목표의 자리·크기는 이어 준다**(`Smooth`, 사용자 2026-09-18 "돌고 멈췄다가 머리로"): 새 사각형으로 바로 안 바꾸고 예상 자리에서 가로 60%·세로와 크기 35% 만 따라간다.
  가만히 있는 봇의 사각형도 가운데가 세로 중간값 17px(표준편차 28)·가로 11px 흔들려(로그 2,666쌍), 크게 돈 뒤 흔들린 머리로 한 번 더 움직였다.
  두 번 보고 고른 먼 목표는 두 사각형의 평균으로 첫 조준을 한다. `가장가까운검출()`·`검출들()` 은 그대로 날것.
- **`조준(검출)` 은 조준 스레드**(`AimLoop`, 사용자 2026-09-18 "부자연스러워" - 옛 한 번짜리 조준은 로그 434회에 움직임 76ms·멈춤 249ms, 움직이는 시간 22%):
  붙잡은 검출을 향해 **8ms 마다 멈추지 않고** 움직인다. 모형은 화면 가운데 기준 거리(px) = 본 거리 + 속도×시간 − (그 뒤 보낸 카운트)÷배율. 보낸 카운트는 시각과 함께 적고,
  프레임은 입력→화면 지연(`_latencyMs` = 110) 앞의 입력까지만 반영한 것으로 본다. **지연은 넉넉히 못 박고, 보내는 양이 막 바뀌는 중에 온 화면은 덜 믿는다**(`Trust` - 지연을 모르는 띠 40~200ms 안에 보낸 양이
  프레임 사이에 달라진 만큼이 불확실함, 24px 에서 절반). 짧게(40) 잡았더니 아직 안 보인 입력을 반영된 줄 알고 더 보내 큰 조준의 32% 가 20px 넘게 지나쳤고(사용자 "너무 휙휙", 실측: 붙인 뒤 움직임이 화면에 보이기까지 중간값 164ms),
  후보를 견줘 스스로 고르게 했더니 오차가 비슷해 40↔70↔100 을 오가며 79% 가 지나쳤다. 길게 잡는 쪽은 틀려도 덜 보내 느릴 뿐이다. 예측과의 차이가 8px 아래면 떨림으로 보고 0.4 만, 24px 넘으면 그대로, 그 사이는 고르게 받는다(`Calm` - 8px 에서 뚝 끊기면 떨림 10px 짜리를 통째로 받아 붙은 직후 ±10px 을 오갔다).
  남긴 것을 푼 직후 0.3초는 예측과의 차이를 지연 70·110·130ms 세 가정으로 재어 어느 쪽으로 봐도 남는 만큼만 받는다(`Cautious`) - 기준 지연 하나로만 재면 그 짧은 움직임 뒤에 "지나쳤다" 로 읽고
  18px 을 물러났다. 늘 그렇게 하면 달리는 검출을 따라가는 동안 가정들이 늘 12px 갈려 죽은 띠가 된다(10px 뒤에서 쫓음).
  **움직임은 잘 겨누는 사람의 손처럼**(사용자 2026-09-18 "움직임이 너무 허술해 · 프로게이머처럼"): 가속 상한(6.3px/박자) → 속도 상한(3.9px/ms, px 기준 - 카운트로 두면 감도마다 달라진다)
  → **일정 감속**(√(2·0.076·거리)) → 마지막 수십 px 만 1차 접근(멀면 22ms·붙으면 45ms) + 검출 속도 앞먹임, 1.5px 안은 안 움직임. 속도가 종 모양이라 빠르게 올렸다 딱 선다 -
  1차 접근만 쓰던 때(시간 상수 95ms)는 끝이 지수 꼬리라 300px → 20px 에 344ms 였다. **크게 꺾을 때(60px 넘게)**는 끝난 뒤 그 결과가 다 담긴 화면(프레임 − 100ms 가 첫 움직임 끝보다 뒤,
  "확인 화면")을 가려 그대로 믿는다. **200px 넘는 꺾기는 두 번에 나눈다**: 첫 움직임은 일부러 못 미치게 던지고(`ShortfallFraction`, 200px 부터 늘어 300px 에서 8%) 확인 화면을 보고 남긴 것을
  풀어 다듬는다(0.45초 넘게 안 오면 그냥 푼다). 0.13초짜리 꺾기는 도중에 화면으로 못 고쳐 정확도가 배율에 달렸는데 잰 배율은 ±15% 흩어진다 - 끝까지 가면 300px 에서 45px 를 지나쳐 되돌아온다.
  200px 아래는 남기지 않는다(실측 2026-09-18: 사격장 봇은 옆으로 걷는데 확인 화면을 기다리며 서 있는 141ms(90% 235) 동안 20~35px 달아나, 100~200px 꺾기 33번 중 32번이 20% 모자란 채 멈춰 있었다 -
  그 거리에서 배율 15% 오차는 몸 안이다). 확인 화면은 **배율 표본**으로도 쓴다(꺾기 전 본 자리 → 지금, 그 사이 보낸 전부 - 첫 움직임 뒤로 거의 안 보내 지연과 무관, 큰 꺾기마다 하나.
  꺾기 전 자리에 반영됐는지 모르는 입력이 꺾은 양의 15% 를 넘거나 검출이 걷고 있었으면 안 준다).
  **붙이는 순간 검출의 속도를 미리 잰다**(`SeedVelocity` - 허브 스냅샷의 `Previous`, 우리가 가만히 있던 두 장): 붙인 뒤에야 재면 꺾는 동안은 못 재서 걷는 봇을 선 봇으로 알고 꺾었다.
  **화면에 찍힌 검출의 자리도 지연만큼 옛것**이라 속도 × 90ms(`DetectionLeadMs`)를 앞서 겨눈다(가짜 게임도 검출의 자리를 지연만큼 늦게 준다). 예측과의 차이가 한쪽으로 이어지면 속도에도 조금 보탠다
  (`VelocityBeta` α-β) - 자리만 고치면 떨림을 누르느라 걷는 봇 뒤 20~30px 에 1초 넘게 머물렀다.
  **같은 검출로 볼 문은 좁다**(`GateSizeFactor` 몸 크기 0.6배 + 검출이 갈 수 있는 만큼 + 우리가 돌린 양의 25%, 사각형 높이가 0.6~1.6배 안): 날것에는 옆 봇도 그대로 들어 있어 크기×2 로 열면 붙잡은 봇이
  한 장 안 보일 때 옆 봇으로 건너뛰었다(실측: 가만히 겨눈 프레임 쌍의 7%, 한 번은 650px - 그 쌍의 배율 표본 7~9.6 이 배율을 3.3↔4.3 으로 흔들었다).
  **가만히 겨누는데 3장(150ms) 넘게 안 보이면 바로 놓는다**(죽은 봇 - 붙인 142번 중 49번이 400ms 를 다 기다렸다). 꺾는 중의 놓침은 화면 번짐일 수 있어 400ms 기다린다.
  **조준 스레드는 화면용 추적기를 안 거친 날것 검출을 본다**(`DetectionSnapshot.Raw`·`ForAiming`). 추적기(`DetectionTracker`)는 직전 자리와 6:4 로 섞고 못 이으면 옛 사각형을 두 번 더 내준다 -
  조준이 화면을 돌리는 중에는 옛 화면 좌표에 끌린 늦은 자리라, "검출이 달아났다" 로 읽고 더 밀었다(실측 로그: 344 카운트를 보냈는데 본 자리 -60 → -60 → -60 → +48 → +75, -159px 에서 +75px 로
  지나친 뒤 1초에 걸쳐 복귀). "휙휙"·"허술" 의 뿌리가 이것이었다 - 하네스에서 추적기 사각형을 보게 하면 지나침 49px, 날것이면 2px. `목표()` 가 고르는 것은 그대로 추적기 결과(헛것 거르기).
  **속도는 우리가 휙 꺾는 중이던 프레임 쌍으로는 안 잰다**(`DetectionVelocity` - 지연을 60~160ms 로 가정해 우리가 돌린 속도가 0.9px/ms 를 넘는 것이 있으면 건너뜀): 지연 20ms 차이가 가짜 속도 0.78px/ms 가 되어
  앞먹임이 조준을 목표 옆 10~15px 에 1초씩 걸어 뒀다. 가정들이 엇갈린 폭만큼 속도를 줄이는 방식은 안 됐다(작게 알면 몰아서 보내고 그러면 폭이 더 커져 0 으로 붙는다 - 달리는 검출을 20px 뒤에서 쫓음).
  **붙으면 쉰다**(`RestInPx` 4px 안에 들면 서고 8px 를 넘어야 다시 움직임, 80px/s 아래 속도는 0 - 사용자 2026-09-18 "화면이 너무 떨려·헛발": 붙은 프레임마다 4~20px 을 보내고 있었다).
  속도 상한은 400px/s, 한 프레임에 450px/s 넘게 뛰면 다른 검출이거나 사각형이 튄 것으로 보고 속도를 0 으로(1.5px/ms 였을 때 사각형이 한 장 40px 튄 것을 −363·+619px/s 로 받아
  100~180px 꺾기가 반대편으로 87~89px 지나쳤다). 붙인 뒤 처음 잰 속도는 반만 믿고 두 번째부터 다 믿는다(붙일 때 미리 잰 것은 바로 다).
  값은 실측에 맞춘 가짜 게임 `SimHub`(0.1초 프레임·90ms 지연·±5px 떨림)에서 맞췄다(`--aim`): 300px 을 0.1초에 40px 안(몸 안), 0.3초에 머리 20px 안·지나침 4~7px·붙은 뒤 흔들림 4px, 200px/s 로 달아나는 검출을 0.3초에 따라잡아 평균 2~5px·가장 멀 때 8px,
  옆(120px)에 다른 봇이 있고 네 장에 한 번 안 보여도 안 건너뜀(붙은 뒤 14~17px 안), 배율이 15% 과해도 지나침 9~11px, 배율 2.0 에서 시작해 봇 12마리에 2~3번 고쳐 3.5 근처. 새 검출이 오면 프레임 시각의 예상 자리에서 가장 가까운 것(크기×2 + 속도 여유)을 같은 검출로 보고 차이를 가로 75%·세로 55% 만(거기에 믿음·떨림 비율을 곱해) 받아들인다.
  **검출 주기는 45ms**(80 에서, `DetectIntervalMs`) - 확인 화면을 기다리는 시간이 곧 머리에 붙는 시간이다. GPU 몫이 14% → 25% 안팎으로 는다(추론 중간값 14ms) - 게임 fps 가 떨어지면 올린다.
  400ms 못 보면 놓는다(그때 `목표()` 가 새로 고른다). `조준(검출)` 을 부르면 **새 화면이 한 장 올 때까지**(최대 400ms) 기다렸다 몸 사각형 안이면 true - 한 화면에 한 번만.
  스레드가 붙잡고 있는 동안 `목표()` 는 스레드의 예측 자리를 준다. 놓는 곳: `목표풀기`·상대이동·끌기·좌표 조준·일시정지·중지·앞 창 바뀜. 배율 배우기는 **멈춰 서 있던 프레임(닻)→지금** 보낸 총량 ÷ 줄어든 거리로, 모르는 부분(띠 안에 보낸 양)이 총량의 15% 아래일 때 닻마다 한 번. 보낸 쪽과 줄어든 쪽이 반대면(다른 봇으로 이어 붙음) 버린다.
  `--vision` 의 `조준(검출):` 세 줄(붙기·달리는 검출·배율 배우기) + `목표풀기` 한 줄 - 닫힌 고리 가짜 허브 `SimHub`(보낸 카운트만큼 돌아간 화면, 50ms 프레임, 30ms 지연).
- **게임에서는 `이동()` 이 안 먹는다**(Raw Input 은 움직인 양만 본다) - `조준(x, y)` = 창 가운데에서 목표까지 × 배율만큼 상대 이동(`MoveMouseBy`), 한 번짜리.
- **같은 화면으로 두 번 겨누지 않는다** - 스냅샷 `FrameTicks` 가 마지막 조준보다 앞이면 건너뛰고, 새 화면을 1.5초까지 기다렸다 false. 판단은 스크립트가 본 스냅샷으로.
- **조준은 "맞았나" 를 돌려준다** - 새 화면에서 가운데 8px 안이면 true. 겨눈 뒤 80ms 안의 프레임은 겨누기 전 화면으로 본다.
- **85% 만 보낸다**(`AimDamping`) - 지나치면 왕복한다. 한 번에 보내는 양은 1,200 카운트까지.
- **배율은 스스로 배운다**(`IsAimScaleAuto`, 기본 켬). 되먹임으로 상한까지 떠밀린 적이 있어(실측 3.6 → 20) 셋을 지킨다:
  40~400px 조준으로만 배운다(작으면 사각형 흔들림, 크면 화면 가장자리 왜곡) · **아홉 번 잰 것의 가운뎃값**(`AimSamples`, 잡음이 한쪽으로만 튄다) ·
  상한에 잘린 조준으로는 안 배운다. "지나침" 도 배운다(결국 가까워졌으면 비율 2.0 까지) - 안 그러면 과한 배율을 못 내린다. 보낸 양은 자른 뒤의 값으로 적는다.
- **이동은 사람이 겨누듯 나눈다**(`SendRelative`) - 한 번에 수백을 넣으면 OS 커서가 창 밖으로 나가 바탕 화면을 눌렀다.
  S자(smoothstep) · 8ms 마다 · `70 + 6.5·√거리` ms(상한 280ms·40걸음) · 옆으로 거리의 2%(최대 12) 벗어났다 돌아옴 - 합은 정확히 delta.
- **윈도우 시계 눈금을 당긴다**(`PrecisionTimer`, `timeBeginPeriod(1)`) - 기본 15.6ms 라 8ms 를 부탁해도 15.6ms 를 쉰다. 시스템 전체 값이라 **움직이는 동안만** 켠다.
  걸음 사이는 `WaitPrecise`(1.5ms 아래면 스핀) + 중지 토큰.
- OS 커서는 보낸 카운트보다 많이 움직인다(60 → 135px, 포인터 정밀도) - 게임은 카운트를 그대로 보니 조준 배율과 섞지 않는다.
- 걷기·누르고 있기(`걷기("W", 500)`·`클릭(100)`)는 finally 로 반드시 떼고, 누른 것은 적어 두어 비상 정지가 뗀다.

## 입력 경로

- **SendInput 키에는 스캔코드를 싣는다** - wScan 0 이면 Raw Input 게임에 W·A·S·D 가 안 먹는다. 확장 키는 `VirtualKeys.IsExtendedKey`.
- **대상이 관리자면 이 앱도 관리자여야 한다**(UIPI - SendInput 도 전역 단축키도 막힌다). `ProcessElevation` 이 견줘 "관리자로 다시 시작" 을 보인다. Interception 은 입력은 넣지만 단축키는 여전히 안 온다.
- **Interception 은 사람이 쓰는 그 장치 자리로 보낸다** - 첫 자리로만 보냈더니 마우스가 둘 붙은 PC 에서 게임이 무시했다.
  `RawInputDeviceTracker` 가 마지막으로 쓴 장치를 기억하고 `InterceptionInputAdapter.Resolve` 가 하드웨어 ID·VID·PID·MI 로 자리를 고른다. `--interception-probe`(실제 입력).

## 전역 단축키

- **공용**(`SharedHotkeysFactory.Default`) - RegisterHotKey 는 한 조합을 한 창만 쥔다. 화면은 `Claim` 으로 쥐고(`HotkeyClaim`) 탭이 활성화되면 차례를 당긴다 - **마지막에 본 화면이 받는다**.
- 스크립트 화면: F5 실행/계속 · F6 중지 · F10 한 줄 · Pause 비상 정지(도는 동안) · F9 는 VS 처럼 중단점용으로 비워 둔다. 플레이: F5 1회 · F6 반복/중지. 화면캡처·스크립트: F8 담기.
- 호출 로그(`ScriptConsole.Trace`)는 파일 로그에도 Debug 로 남긴다. 출력 칸은 칸마다 화면 갱신을 하나만, 파일 로그는 같은 호출·결과를 건너뛰고 센다(쉬기 없는 반복문 대책).

## 디버그 (스크립트 화면)

- **호출 로그**: API 호출마다 `ScriptCall`(시각·이름·인자·결과·걸린 시간) → `ScriptConsole.CallsText`(최근 200개). C# 은 한 줄씩 밟을 수 없어 이것이 디버거 몫이다. `쉬기()` 는 500ms 이상만.
- **중단점·한 줄씩**은 `ScriptDebugSession` - UI 는 `Breakpoints` 를 고치고, 엔진은 줄마다 `ShouldBreak`·`Pause`. 스레드용 집합을 따로 둔다. 멈춘 채 중지하면 토큰이 깨운다.
  - JavaScript: Jint 디버거(`Debugger.Step`), 사용자 글에 이름을 붙여 우리 껍데기 함수와 가른다.
  - Python: `sys.settrace`, `co_filename == '<script>'` 줄에서만. 멈춘 동안 GIL 을 쥔 채 기다린다.
  - C#: `SupportsStepping=false`.
- **일시정지는 둘**(사용자, 2026-09-17 - 한 단추가 캡처·실행을 같이 멈추니 실행 옆에서 "실행 후 일시정지" 로 읽혔다):
  디버그 도구 줄·메뉴 `실행 일시정지`(`ScriptStudioViewModel.IsPaused`, 도는 스크립트만) · 캡처 도구 모음·메뉴 `캡처 일시정지`(`CaptureViewModelBase.IsCapturePaused`, 캡처가 돌 때만 켜짐 - 플레이 화면에도).
  캡처 일시정지는 세션은 두고 프레임을 흘려 미리보기(마지막 장)·검출·계속 읽기·허브 올리기를 쉰다(통계·저장·담기는 돈다).
  대상이 **영상**이면 재생도 멈춘다(`IPausableCapture` - 영상 세션과 공유 손잡이, 시계를 멈춘 만큼 민다). 프레임만 흘렸더니 영상은 계속 흘러갔다. 같은 영상을 나눠 쓰는 화면이 있으면 그 화면도 멈춘다.
  실행 일시정지는 `LiveScriptSession.PauseGate`(`ScriptPauseGate`) - C# 은 줄마다 못 멈춰 **API 호출에서** 멈춘다(`Traced` 앞·`쉬기` 50ms 조각마다, 남은 쉬기는 멈춘 만큼 민다). API 를 안 부르는 계산 반복문은 못 멈춘다.
  멈출 때 누르던 키·버튼을 뗀다(`ReleaseAll`), 계속할 때 대상 창을 앞으로 가져온 뒤 연다(안 그러면 앞 창 안전장치에 막힌다). 실행 일시정지의 계속은 다시 누르거나 F5, 실행이 끝나면 풀린다. 캡처 일시정지는 캡처를 멈추면 풀린다. Pause 키는 비상 정지 그대로.
  검사 `--vision` 의 `일시정지:` 두 줄.
- 편집기 왼쪽 여백(`BreakpointMargin`) 클릭·Ctrl+B = 중단점. 여백은 `OnRender` 에 투명 판을 깔아야 클릭이 온다.

## 검증

`--vision` 의 실시간 검사는 **가짜 어댑터**(누른 것을 적기만)와 가짜 허브로 돈다 - 입력은 절대 실제로 안 나간다.
조준 배율·목표·JS 중단점(2번 줄·변수 `a=1`)·한 줄씩·멈춘 채 중지·호출 로그·공용 단축키를 본다.

# 스크립트로 검출·글자·키 입력을 다루는 구조 설계

2026-09-11. 요청: "검출, 키 입력 등 스크립트에서 조정하고 싶어 구조적으로 설계해줘",
"이 화면에 스크립트 편집 화면 넣어주면 되겠다. 문법, Code Complete, 빨간 밑줄, 문법 검사, 디버깅, 디버깅 창".

## 1. 지금 있는 것과 없는 것

있는 것
- 세 언어 엔진(`Input/Scripting`): C#(Roslyn) · Python(Python.NET) · JavaScript(Jint). 공통 얼굴은 `IScriptEngine`.
- 스크립트가 부르는 API `SequenceScriptApi`(글자·엔터·클릭·이동·휠·쉬기, 한글 이름 포함).
- 편집기: AvalonEdit(`Markup/ScriptEditor`) + 언어별 문법 색. 500ms 디바운스로 컴파일해 "고칠 줄" 칸에 오류 문장을 띄운다.
- 오류마다 **줄 번호**가 이미 온다(`ScriptError(Line, Message)`, 세 엔진 모두).
- 캡처 모니터: 프레임 → 몹 찾기(검출·추적) → 이름표 OCR → 미리보기. 결과는 캡처 모니터 ViewModel 안에만 있다.

없는 것
- 스크립트는 **계획만 적는다**. 돌리면 단계 목록이 나오고, 그 목록을 나중에 순서대로 보낸다.
  "몹이 보이면 클릭" 처럼 **실행 도중에 화면을 읽고 판단하는 것**이 불가능하다.
- 검출·OCR 결과를 다른 화면이나 스크립트가 읽을 통로가 없다.
- 코드 완성, 빨간 밑줄, 중단점, 디버그 창.

## 2. 핵심 결정: 실행 모드를 둘로 나눈다

| | 계획 모드(지금) | 실시간 모드(새로) |
|---|---|---|
| 스크립트가 도는 때 | 미리 한 번 | 시작을 누른 뒤, 끝날 때까지 |
| 입력 | 단계 목록에 적힘 → 나중에 전송 | 부르는 즉시 전송 |
| 화면 읽기 | 못 함 | `찾기()`·`글자()` 로 지금 프레임을 읽음 |
| 장점 | 순서 미리보기, 반복, 검토 | 조건·반응 가능 |
| 쓰임 | 정해진 타이핑·클릭 | 게임처럼 화면을 보고 움직이는 일 |

계획 모드를 없애지 않는다. 지금 사용자가 쓰는 시퀀스 미리보기·반복·중지가 그 위에 서 있고, 정해진 입력에는 그쪽이 더 안전하다.
두 모드는 **같은 API 이름**을 쓴다. `클릭()` 은 계획 모드에서는 적히고 실시간 모드에서는 나간다. 스크립트를 옮겨 다닐 수 있어야 사람이 두 벌을 배우지 않는다.

## 3. 계층

```
┌ 화면 ──────────────────────────────────────────────────────────┐
│ 캡처 모니터 ─┐                     스크립트 칸(편집기·디버그 창) │
│ 라벨링       │ 인식 결과 올림                 │ 읽음 · 입력 보냄  │
└──────────────┼────────────────────────────────┼───────────────────┘
               ▼                                ▼
┌ 인식 허브 PerceptionHub ─────┐   ┌ 스크립트 실행기 LiveScriptRunner ┐
│ 마지막 프레임(참조·크기·시각) │◄──│ 백그라운드 스레드, 중지 토큰,     │
│ 마지막 검출 목록(추적 포함)   │   │ 초당 호출 상한, 비상 정지(F9)     │
│ 마지막 OCR 결과(영역·이름표)  │   └──────────────┬───────────────────┘
└───────────────────────────────┘                  │
                                                   ▼
┌ 스크립트 API (ScriptApiCatalog 가 이름·설명·시그니처의 단일 출처) ─┐
│ 찾기 = 검출     글자 = OCR     입력 = 키·마우스     시간 = 기다리기 │
│ 계획 모드 구현: SequenceScriptApi(있음)   실시간 구현: LiveScriptApi │
└─────────────────────────────┬────────────────────────────────────┘
                              ▼
        InputService(있음)  ·  DetectorModel(있음)  ·  IOcrEngine(있음)
```

### 3.1 인식 허브 `Vision/PerceptionHub` (새로)
- 앱에 하나. 캡처 모니터가 프레임마다 `Publish(frame)`, 검출이 끝날 때 `Publish(detections)`, OCR 이 끝날 때 `Publish(ocr)`.
- 읽는 쪽은 **복사본**을 받는다(불변 레코드 + 시각). 스크립트 스레드가 캡처 스레드를 잡지 않게.
- 캡처 모니터가 꺼져 있으면 `찾기()` 는 "눈이 없다: 캡처 모니터에서 시작을 누르세요" 예외. 조용히 빈 목록을 주면 스크립트가 왜 아무것도 못 찾는지 알 수 없다.
- 인터페이스 `IPerceptionHub` + 구현 + 팩터리(CLAUDE.md 규칙). 하네스는 가짜 허브를 꽂아 스크립트를 화면 없이 검증한다.

### 3.2 스크립트 API `Input/Scripting/Api`
스크립트 안에서 전역처럼 보이는 것들. 영문·한글 이름 쌍.

```
검출
  몹들()            → Mob[]   지금 프레임의 검출(추적 후). Mob: 이름, 점수, 중심x, 중심y, 너비, 높이, 이름표
  가장가까운몹()    → Mob?    화면 중앙에서 가장 가까운 것
  몹기다리기(ms)    → Mob?    보일 때까지 최대 ms 기다림
글자
  글자(영역)        → string  영역(0~1 비율 사각형 또는 이름)의 OCR. 영역 이름은 캡처 모니터에서 저장한 것
  숫자(영역)        → int?    글자에서 숫자만
입력 (있음: 글자·줄입력·엔터·한영·클릭·우클릭·이동·이동클릭·휠·쉬기)
  키(이름)                    "F", "Space", "Shift+1" 같은 이름
  누르기(이름) / 떼기(이름)   길게 누르기
  이동(x, y)                  픽셀. 몹 좌표를 그대로 넣을 수 있게 화면 픽셀로 통일
시간·흐름
  기다리기(ms)  · 시각()  · 중지되었나()  · 끝()
관찰
  출력(값)      → 디버그 창에 찍힘
  보기(이름, 값) → 디버그 창 "변수" 칸에 최신값으로 남음
```

- 좌표는 **캡처 대상 창의 클라이언트 픽셀**. 검출은 0~1 비율로 들고 있으니 허브가 프레임 크기로 곱해 준다. 대상 창이 옮겨져도 스크립트는 모른 채로 맞다.
- `ScriptApiCatalog`: 이름(영·한), 매개변수, 한 줄 설명, 어느 모드에서 되는지를 표로 든다. 세 엔진의 바인딩(지금은 각자 손으로 적어 둔 목록)과 **코드 완성 목록**과 **도움말**이 모두 이 표에서 나온다. 한 곳만 고치면 세 언어·완성·문서가 같이 맞는다.

### 3.3 실시간 실행기 `Input/Scripting/LiveScriptRunner`
- 스크립트를 전용 스레드에서 돈다. UI 스레드가 아니다(Python GIL, Roslyn 대기 때문에도).
- **안전장치** (전부 기본 켜짐)
  - 비상 정지 전역 핫키(F9): 어느 창에 있어도 즉시 중지, 누르고 있던 키를 모두 뗀다.
  - 대상 창이 앞에 없으면 입력을 보내지 않고 스크립트에 예외. 엉뚱한 창에 타이핑하는 사고 방지.
  - 초당 입력 호출 상한(기본 30). 무한 루프에서 입력이 폭주하지 않게.
  - 한 번 실행 시간 상한(기본 10분, 설정).
  - 마우스가 게임에 잡혀 있을 때 `이동` 은 상대 이동으로 바꿔 보낸다(캡처 모니터의 "입력 전달" 과 같은 규칙).
- 상태는 `IScriptSession`(시작 시각, 호출 수, 마지막 줄, 오류)로 디버그 창에 흐른다.

### 3.4 편집기
| 기능 | 방법 | 크기 |
|---|---|---|
| 문법 색 | 있음(AvalonEdit xshd) | - |
| 문법 검사 | 있음(500ms 디바운스 컴파일). 결과를 문장 대신 `ScriptError[]` 로 편집기에 넘김 | 작음 |
| 빨간 밑줄 | `IBackgroundRenderer` 로 오류 줄에 물결선, 마우스 올리면 문장 툴팁. 세 엔진이 줄 번호를 이미 준다 | 작음 |
| 코드 완성(공통) | `CompletionWindow` + `ScriptApiCatalog`. 한글·영문 이름, 매개변수 힌트, 설명. 세 언어 모두 같은 목록 | 작음~중간 |
| 코드 완성(C# 전체) | Roslyn `CompletionService`. `Microsoft.CodeAnalysis.CSharp.Features`+`Workspaces` 패키지 추가(수십 MB, 첫 호출 1~2초). 지역 변수·`string` 멤버까지 나온다 | 중간, **선택** |
| 코드 완성(Python·JS 전체) | 각 런타임 안의 리플렉션(Python `dir()`, Jint 전역)으로 **실행 후** 보이는 이름만. 정적 분석기(Jedi 등)는 넣지 않는다 - 무겁고 얻는 것이 적다 | 작음, 뒤로 |

편집기 컨트롤은 입력 자동화와 새 스크립트 칸이 **하나를 공유**한다(`Markup/ScriptEditor` 확장). 두 벌이면 밑줄·완성이 한쪽에만 붙는 일이 생긴다.

### 3.5 디버깅
언어마다 할 수 있는 것이 다르다. 공통 얼굴 `IScriptDebugger` 를 두고 못 하는 것은 "이 언어에서는 안 됨" 으로 회색 처리한다.

| | JavaScript(Jint) | Python | C#(Roslyn 스크립트) |
|---|---|---|---|
| 중단점 | 됨(`DebugHandler.BreakPoints`) | 됨(`sys.settrace`) | **안 됨** |
| 한 줄씩 | 됨(`StepMode`) | 됨 | 안 됨 |
| 지역 변수 | 됨 | 됨(`frame.f_locals`) | 안 됨 |
| 현재 줄 강조 | 됨 | 됨 | 호출한 API 줄만(호출 추적) |
| 출력·보기 | 됨 | 됨 | 됨 |

C# 은 Roslyn 스크립트가 디버거 없이 도는 구조라 스텝이 없다. 대신 **호출 추적**(API 를 부를 때마다 시각·인자·결과·줄 번호 기록)과 `보기()` 로 메운다. 한 줄씩 밟아야 하면 JS 나 Python 을 권한다 - 화면 안내문으로 적는다.

디버그 창(스크립트 칸 아래, 접이식)
- **출력**: `출력()` 과 print/console.log.
- **호출**: 시각 · 함수 · 인자 · 결과 · 걸린 시간. 실시간 모드의 사실상 로그.
- **변수**: `보기()` 값과(지원 언어면) 중단된 자리의 지역 변수.
- **중단점**: 편집기 여백 클릭으로 켜고 끔. 목록에서 한꺼번에 해제.
- 도구 줄: 실행 · 중단점까지 · 한 줄 · 계속 · 중지.

## 4. 스크립트 예시 (실시간 모드)

C#
```csharp
while (!중지되었나())
{
    var 몹 = 가장가까운몹();
    if (몹 is null) { 기다리기(100); continue; }

    보기("대상", $"{몹.이름} {몹.점수:P0} 「{몹.이름표}」");
    이동(몹.중심x, 몹.중심y);
    클릭();
    기다리기(300);
}
```

Python
```python
while not 중지되었나():
    몹 = 가장가까운몹()
    if 몹 is None:
        기다리기(100); continue
    출력(f"{몹.이름} {몹.점수:.0%}")
    이동(몹.중심x, 몹.중심y); 클릭(); 기다리기(300)
```

같은 글을 계획 모드에서 돌리면 `가장가까운몹()` 이 "실시간 모드에서만 됩니다(3번째 줄)" 로 빨간 밑줄이 된다. 모드 표는 카탈로그에 있다.

## 5. 화면 넷으로 나눈다

요청: "화면을 캡처하는 곳, 라벨링 하는 곳, 화면 인식하면서 스크립트 편집하는 곳, 플레이 하는 곳".

| 화면 | 하는 일 | 남기는 것 | 안 하는 것 |
|---|---|---|---|
| **캡처** | 대상 창 고르기, fps, 미리보기, 데이터셋에 담기(F8), 프레임 저장, 통계 | 데이터셋 그림 | 검출·OCR·스크립트 |
| **라벨링** | 사각형 그리기·고치기, 앞 장 가져오기, 점선 받기, 학습, 인식률 | 모델(`detector.zip`) | 캡처·입력 |
| **스크립트**(개발) | 몹 찾기·추적·OCR 을 켜 놓고 보면서 스크립트를 쓰고, 밑줄·완성·디버그 창으로 고친다. 실행은 **한 번씩**, 비상 정지 | 스크립트 파일 | 반복 실행, 담기 |
| **플레이** | 스크립트 하나를 골라 시작·중지. 미리보기는 작게(또는 끔), 호출 로그와 상태만. 다른 PC 에서 이것만 연다 | 실행 기록 | 편집, 학습, 담기 |

왜 넷인가
- 캡처 모니터 하나에 담기·검출·OCR·(앞으로) 스크립트까지 얹으니 도구 줄이 넘쳤다(글자 상태 칸이 밀려난 것이 그 신호).
- 플레이하는 PC 에는 편집기·라벨링·학습이 없어야 한다. 화면이 나뉘어 있어야 "플레이만" 이 한 탭이 된다.
- 개발 화면과 플레이 화면은 **같은 실행기**를 쓰고 껍데기만 다르다. 개발에서 되던 것이 플레이에서 안 되는 일이 없게.

나누면 생기는 구조 변화 (이것이 진짜 일이다)
- 지금 캡처·검출·OCR 은 **캡처 모니터 ViewModel 안**에 있다. 스크립트 화면과 플레이 화면도 프레임과 검출이 필요하므로,
  이것을 화면 밖 **앱 서비스**로 뺀다: `ICaptureSession`(대상·fps·시작·중지·프레임 이벤트) 과 `IPerceptionHub`(3.1).
  네 화면은 같은 세션을 **함께 본다** - 캡처 화면에서 시작한 캡처를 스크립트 화면이 그대로 받고, 플레이 화면은
  제 힘으로 시작할 수 있다. 데이터셋 자리를 앱 전체 키 하나로 둔 것과 같은 이유다(화면마다 들면 왜 안 보이는지 찾게 된다).
- 미리보기 그리기(`DetectionOverlay`, 입력 전달, 글자 영역 끌기)는 **컨트롤**로 떼어 세 화면(캡처·스크립트·플레이)이 얹는다.
- 캡처 모니터 ViewModel 은 캡처 화면으로 줄어든다. 검출·OCR 부분(`.Detect.cs`, `.Ocr.cs`)은 서비스로 옮긴다.
- 설정 키는 화면별이 아니라 서비스 것으로 옮긴다(대상 창, fps, 문턱, 추적, OCR 언어·영역). 옮길 때 예전 키를 한 번 읽어 넘긴다.
- 메뉴: 대시보드 · 캡처 · 라벨링 · 스크립트 · 플레이 · 입력 자동화. 입력 자동화는 계획 모드 스크립트 화면으로 남는다.

스크립트 파일은 `%AppData%\Minguk.Tools\Scripts\<이름>.<cs|py|js>`(있음: `ScriptFiles`). 플레이 화면은 이 폴더에서 고른다.

## 6. 단계와 순서

0. **화면 넷으로 분리** - 2026-09-11 에 했다. 서비스로 빼는 대신 **베이스 클래스**로 나눴다:
   `CaptureViewModelBase`(잡기·미리보기·입력 전달·담기) ← `RecognizingCaptureViewModelBase`(몹 찾기·OCR) ←
   편집(`ScriptStudioViewModel`)·플레이(`PlayViewModel`). 캡처(`CaptureMonitorViewModel`)는 첫 바탕만 쓴다.
   스크립트 문서는 `ScriptWorkbench`, 실행은 `ScriptPlayer` 로 떼어 두 화면이 같이 쓴다. 미리보기 판과 입력 전달
   도구 줄은 `Views/Parts` 의 UserControl 이다. 화면마다 제 캡처 세션을 든다(공유 세션·`IPerceptionHub` 는 2단계에서).
   입력 자동화 화면은 아직 제 스크립트 코드를 들고 있다 - `ScriptWorkbench` 로 옮기는 것이 1단계 앞에 온다.
1. **밑줄 + 공통 완성** (편집기만, 위험 없음)
   `ScriptError[]` 를 편집기로, 물결선 렌더러, `ScriptApiCatalog` 와 `CompletionWindow`. 세 엔진의 바인딩을 카탈로그에서 나오게 정리. `--views` 로 밑줄 픽셀·완성 목록 검사.
2. **인식 허브 + 실시간 API + 실행기 + 비상 정지**
   캡처 모니터가 허브에 올리고, `LiveScriptApi` 가 읽고 보낸다. 하네스는 가짜 허브·가짜 입력으로 스크립트가 맞는 좌표에 클릭하는지 센다. **실제 게임으로는 보내지 않고 검증한다**(내 창에만).
3. **디버그 창 + 호출 추적 + JS/Python 중단점·스텝**
   `IScriptDebugger`, Jint `DebugHandler`, Python `sys.settrace`. C# 은 호출 추적만.
4. **C# 전체 완성(Roslyn Features)** - 패키지 무게를 보고 결정.

각 단계가 따로 커밋되고 따로 돌아간다. 0단계가 가장 크고(옮기기), 1단계는 0단계 없이도 붙는다 - 순서를 바꿔도 된다.

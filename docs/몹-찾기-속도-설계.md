# 몹 찾기 속도 설계 - ONNX 검출기로 가는 길

2026-09-12. 지금 쓰는 검출기가 느린 이유와, 중급 그래픽 카드 한 장으로 게임과 같이 돌리기 위한 설계.
0~4단계는 했고 **5단계(기본 엔진 전환)까지 왔다**(2026-09-13). 결과는 5장 끝에 있다.

## 1. 지금 어떤가

| | GTX 1060 3GB | RTX 4070 Laptop |
|---|---|---|
| 몹 찾기 한 번 | 460~700 ms | 270~385 ms (보통 330) |
| 게임이 같이 돌 때 | 700 ms | 480~590 ms |
| 몹 찾기 주기 | 0.7~1.4초 | 0.35초 |

연산력이 4~5배인 카드로 바꿔도 2배밖에 안 줄었다. **카드가 모자란 것이 아니라 쓰는 방식이 느린 것이다.**
넣는 그림 크기는 상관이 없었다(480x270~1080p 모두 660~713ms, 파일 읽기만 0.7→7ms).

느린 까닭은 넷이다.

- **모델**: ML.NET 의 `AutoFormerV2`(트랜스포머 계열). 실시간 검출용으로 만든 것이 아니다.
- **실행**: TorchSharp(libtorch) 로 한 장씩, 32비트 부동소수, 배치 1. 추론 전용 엔진(ONNX Runtime·TensorRT)이 아니다.
- **길**: 프레임을 PNG 로 **디스크에 쓰고 다시 읽는다**(`SaveScaledPng` → `Detect(경로)`).
- **전처리**: 크기 줄이기·정규화를 CPU 에서 한다. 이미 GPU 에 있는 프레임을 내렸다 다시 올린다.

## 2. 목표

**중급 카드 한 장으로, 게임을 돌리면서.** 기준은 RTX 3050·4060 · GTX 1660 급이다.

| | 지금(4070 랩톱) | 목표 |
|---|---|---|
| 몹 찾기 한 번 | 330 ms | **30 ms 이하** |
| 초당 몇 번 | 3회 | **10회 이상** |
| 재현율(같은 데이터셋) | 192개 중 135개 (70%) | **70% 이상** |
| CPU 리드백 | 켜야 함 | **꺼도 됨** |

10회/초면 스크립트 한 바퀴가 0.1초다. 지금은 조준 한 번에 0.35~1.4초를 기다린다.
재현율이 지금보다 떨어지면 채택하지 않는다 - 빠르지만 못 찾으면 쓸모가 없다(480x270 에서 이미 겪었다).

## 3. 이미 있는 것

새로 만들 것이 생각보다 적다. 추론 쪽은 예전에 깔아 둔 것이 그대로 있다.

- `Inference/OnnxDmlEngine` - ONNX Runtime + DirectML 세션. 벤더를 안 가린다(NVIDIA·AMD·Intel).
- `Inference/FramePreprocessor` - **GPU 컴퓨트 셰이더**로 BGRA 텍스처 → 레터박스 → 정규화 텐서. CPU 를 안 거친다.
- `Inference/TensorSpec` - 입력 모양·정규화·레터박스 규약.
- `CapturedFrameEventArgs.Texture` - GPU 에 올라온 프레임 원본. 주석에 "추론을 GPU 에서 돌린다면 이걸 그대로 넘기면 된다" 고 적혀 있다.
- `Microsoft.ML.OnnxRuntime.DirectML` + `Libs\DirectML\x64` - 패키지와 네이티브가 이미 붙어 있다.
- **라벨이 이미 YOLO 형식이다**: `0 0.406498 0.457739 0.064976 0.149322` (분류번호 · 중심x · 중심y · 너비 · 높이, 0~1).
  사진 97장·사각형 192개를 그대로 쓴다.
- 검사 하네스: `--detect-check`(재현율 %) · `--detect-bench`(속도). 둘 다 그대로 새 엔진에 쓴다.

없는 것은 **YOLO 출력 해석(디코더 + NMS)** 과 **학습 경로**뿐이다.

## 4. 핵심 결정

### 4.1 검출기를 인터페이스로 가른다

```
IDetector                      찾는다. 이름·사각형(0~1)·점수를 준다.
 ├ TorchDetector (지금)        ML.NET AutoFormerV2. 파일 경로를 받는다.
 └ OnnxYoloDetector (새로)     ONNX Runtime + DirectML. 텐서를 받는다.
DetectorFactory                모델 폴더의 쪽지(detector.json)를 보고 고른다.
```

쪽지에 `engine: "torch" | "onnx"` 를 넣는다. 지금 모델은 쪽지에 그 칸이 없으므로 `torch` 로 본다 -
**이미 학습해 둔 640x360 모델을 그대로 계속 쓸 수 있어야 한다.** 되돌릴 길을 막지 않는다.

### 4.2 프레임을 파일로 거치지 않는다

지금: `GPU 텍스처 → CPU 리드백 → PNG 저장 → PNG 읽기 → CPU 전처리 → 추론`
새로: `GPU 텍스처 → (컴퓨트 셰이더) 텐서 → 추론`

부수 효과가 크다. **CPU 리드백을 끌 수 있다.** 리드백은 2560x1440 한 장에 수 ms 이고 캡처 fps 를 깎는다.
글자 읽기(OCR)는 여전히 픽셀이 필요하므로, 리드백은 "글자 읽기를 켤 때만" 으로 내려간다.

### 4.3 NMS 는 우리 쪽에서 한다

모델을 내보낼 때 NMS 를 그래프에 넣을 수도 있지만(`nms=True`), 그러면 출력 모양이 내보내기 도구와
ONNX Runtime 판에 따라 달라진다. 출력은 원시 그대로 받고(`[1, 4+클래스수, 후보수]`), 점수 문턱 →
IoU 억제를 C# 에서 한다. 30~40줄이고, 문턱을 화면에서 바꾸는 지금 방식과도 맞는다.

### 4.4 좌표는 레터박스를 되돌려 0~1 로

`FramePreprocessor` 가 비율을 지키며 여백을 채운다(회색 114). 출력 좌표에서 여백을 빼고 배율로 나눠야
원본 화면의 0~1 좌표가 된다. 이 환산이 틀리면 사각형이 조금씩 어긋나는데 눈으로는 잘 안 보인다 -
**`--detect-check` 로 숫자로 본다.**

### 4.5 학습은 앱 밖에서, 앱은 `.onnx` 만 읽는다

`AutoFormerV2` 는 ONNX 로 못 내보낸다(`ICanSaveOnnx` 미구현, 실측). 그러니 YOLO 로 가려면 학습 경로가 따로 필요하다.

- 데이터셋은 이미 YOLO 형식이라 `data.yaml` 한 장만 만들어 주면 된다(내보내기 도구를 앱에 넣는다).
- 학습은 파이썬(Ultralytics 등)에서 돌리고 `best.onnx` 를 데이터셋 폴더에 둔다.
- 앱은 라벨링 화면에서 "ONNX 모델 가져오기" 로 그 파일과 쪽지를 등록한다.

**앱은 C# 만으로 돈다는 원칙은 지킨다** - 파이썬은 학습할 때만, 사람 손으로 한 번 돈다.
libtorch(4.3GB)는 옛 모델을 계속 쓸 동안만 남기고, 새 엔진으로 갈아타면 지울 수 있다.

> 고를 것: 모델 가족. **YOLO11n/YOLOv8n(Ultralytics)** 은 쉽고 빠르지만 라이선스가 AGPL 이다.
> 사내·배포를 생각하면 **YOLOX·RTMDet·NanoDet(Apache-2.0)** 쪽이 안전하다. 속도는 비슷한 급이다.
> 이 결정은 사람이 한다 - 설계는 어느 쪽이든 같다(입력 [1,3,H,W], 출력 [1,후보,4+클래스]).

## 4.6 0단계 실측 (2026-09-12, GTX 1060 3GB · DirectML · FP32)

같은 카드에서 지금 검출기가 **660ms** 다. 사전학습 COCO 모델로 추론 시간만 쟀다(정확도는 안 봄).

| 모델 | 라이선스 | 파일 | 입력 | 추론 한 장 | 초당 |
|---|---|---|---|---|---|
| 지금(AutoFormerV2 · libtorch) | - | 69 MB | 640x360 | **660 ms** | 1.5회 |
| RT-DETR-R18 | Apache-2.0 | 79 MB | 640x640 | **37.3 ms** | 26.8회 |
| D-FINE-N | Apache-2.0 | 15 MB | 640x640 | **29.8 ms** | 33.5회 |
| YOLOX-Nano | Apache-2.0 | 3.7 MB | 416x416 | **5.8 ms** | 171회 |

**여섯 해 전 보급형 카드에서 18~110배다.** 목표(30ms)는 이 카드에서도 사실상 닿았고, 중급 카드면 더 내려간다.
세션 만들기는 0.9~1.1초로 한 번만 든다. 파일 크기는 문제가 아니었다 - 79MB 짜리가 15MB 짜리보다 조금 느릴 뿐이다.

**그러니 0단계는 통과다.** 다음은 정확도를 견주는 일이다(우리 데이터셋으로 학습해 `--detect-check` 재현율 70% 이상).

## 5. 단계와 순서

각 단계가 따로 커밋되고 따로 돌아간다. **앞 단계가 실패하면 거기서 멈춰도 손해가 없다.**

0. **속도만 먼저 잰다** - 아무 사전학습 YOLO `.onnx`(COCO) 를 받아 `OnnxDmlEngine` 에 물리고
   한 장 추론이 몇 ms 인지만 본다. 정확도는 안 본다. 하네스 `--onnx-bench --model=경로`.
   **여기서 30ms 가 안 나오면 나머지 단계는 의미가 없다.** 가장 싸게 확인하는 자리다.
1. **`IDetector` + 팩터리 + 쪽지의 `engine`** - 했다(2026-09-12). `Vision/Inference/IDetector` · `DetectorFactory` ·
   `Vision/Training/DetectorEngine`(Torch·Onnx). `DetectorModel` 이 인터페이스를 구현하고, 화면 셋과 하네스 넷이
   팩터리로 받는다. 쪽지에 `engine` 이 없으면 Torch - 학습해 둔 640x360 모델이 그대로 돈다(`--detect-check` 70%,
   전과 같은 값). `--vision` 이 쪽지 기본값·저장·없는 모델 거절을 본다.
2. **출력 해석 + 레터박스 되돌리기** - 했다(2026-09-12). `Vision/Inference/Onnx/` 에 `LetterboxMap` ·
   `IDetectionDecoder` · `DetrDecoder` · `OnnxDetector`(IDetector 구현). 팩터리가 쪽지 engine=Onnx 면 이것을 준다.
   **DETR 계열은 NMS 가 필요 없다** - 질의 하나가 물체 하나를 맡게 학습돼 같은 것을 여러 번 안 내놓는다.
   YOLO 계열(후보 수천 개 + 겹침 제거)은 실제로 그 모델을 학습하는 4단계에서 붙인다 - 확인할 파일 없이
   미리 쓰지 않는다.
   확인: 사격장 사진 한 장에 COCO RT-DETR 을 물렸더니 봇 둘을 **사람 67%·56%** 로 찾았고, 가운데가
   (0.406, 0.472)·(0.548, 0.466) 이었다. 손으로 찍어 둔 라벨이 (0.4065, 0.4577)·(0.5444, 0.4549) 다 - 1.5% 안쪽.
   `--onnx-detect --model=… --image=… --coco` 가 사각형을 그려 파일로 남긴다. `--vision` 이 레터박스 되돌리기와
   DETR 풀기를 숫자로 본다.
3. **GPU 텍스처 직결** - 했다(2026-09-13). `ITensorDetector`(텐서를 받을 수 있는 검출기만 구현) 를 두고,
   `MaybeDetect` 가 그런 검출기일 때는 캡처 텍스처를 `FramePreprocessor` 로 바로 텐서에 넣는다 - PNG 도,
   CPU 리드백도 안 거친다. ONNX 모델이면 libtorch 요구와 리드백 강제도 건너뛴다.
   확인(`--onnx-texture`): 같은 그림을 CPU 길과 GPU 길로 넣어 **찾은 자리가 소수점까지 같았다**(차이 0.0%).
   셰이더 2.5ms + 텐서 내려받기 15ms(GTX 1060, 파이프라인 끔). 파이프라인은 켜지 않는다 - 0.25초에 한 번
   도는 이 길에서는 "지난 프레임" 이 0.25초 전 화면이라 조준이 옛 자리를 겨눈다.
4. **학습 경로** - 배선은 했다(2026-09-13). 학습 자체는 사람이 한 번 돌린다(`docs/ONNX-모델-학습.md`).
   - `DatasetExport`: `data.yaml`(YOLO 학습기용) · `coco.json`(DETR 학습기용). 사진은 복사하지 않고 원래 자리를
     가리킨다. BOM 없이 쓴다 - 파이썬 json 이 BOM 을 거절한다(실측).
   - `DetectorFiles`: `detector.onnx` 를 들이고(`ImportOnnx`), 어느 모델로 찾을지 고르고(`CurrentFor`),
     한 줄로 되돌린다(`UseTrainedModel`). 하네스는 `--export-dataset` · `--import-onnx` · `--use-trained`.
   - **쪽지는 모델마다 따로**(`detector.json` / `detector.onnx.json`). 하나로 뒀다가 가져오기가 입력 크기를
     640x640 으로 덮어써 640x360 짜리 옛 모델이 재현율 70%→0% 가 됐다(실측). `--vision` 이 이걸 본다.
   - 전 구간 확인: COCO 모델을 들여 `--detect-check` 를 돌리니 97장을 **한 장 152ms**(옛 길 606ms)에 훑었다.
     재현율 22%·헛것 306개는 COCO 모델이라 그렇다 - 배선이 도는지만 본 것이다. 되돌린 뒤 70%로 복귀했다.
   - **우리 데이터로 학습해 갈아 끼웠다**(2026-09-13). D-FINE-N, 97장·60바퀴·1시간 45분(GTX 1060 3GB).
     내보낸 모양이 입력 둘(`images`·`orig_target_sizes`)·출력 셋(`labels`·`boxes`·`scores`)이라
     `OnnxDmlEngine.Run` 에 둘째 입력을 더하고 `DFineDecoder` 를 만들었다. 사각형은 입력 칸 픽셀 xyxy 로
     나오므로 `LetterboxMap.PixelToSource` 가 되돌린다.
   - **조용히 틀리는 것 셋을 만났다.** 셋 다 터지지도 느려지지도 않고 답만 틀린다 - 적어 둔다.
     (1) DirectML 이 `MatMul(행렬, 1차원 벡터)` 의 벡터를 무시하고 행 합계를 낸다(실측).
     D-FINE 디코더의 integral 이 그 모양이라 점수가 0.9 → 0.06 이 되고 192개 중 0개를 찾았다. 헛것도 0개라
     모델이 덜 배운 것처럼 보였다. `도구/onnx-DirectML-고치기.py` 가 벡터를 [N,1] 로 바꿔 고친다.
     (2) 그림 넣는 방식이 학습과 달랐다 - D-FINE 공식 설정은 `Resize [640,640]` 하나뿐이라 늘리기인데
     우리는 비율을 지켜 여백을 넣었다. 쪽지에 `letterbox` 칸을 만들고 `--import-onnx --fit=` 으로 정한다.
     (3) 관리 어셈블리(1.29.0)가 네이티브 ORT(1.24.4)보다 앞서 있었다. 짝을 맞췄다.
   - **다시는 조용히 못 넘어가게** `--import-onnx` 가 들이기 **전에** GPU·CPU 답을 견주고 어긋나면 안 들인다.
     따로 보려면 `--onnx-agree`, 날것 출력은 `--onnx-raw [--cpu]`. 잣대는 CPU 다(같은 모델 105ms, 답은 맞다).

   | | 옛 모델(우리 학습 640x360) | 새 모델(D-FINE-N 640x640) |
   |---|---|---|
   | 재현율 | 135/192 (70%) | **191/192 (99%)** |
   | 헛것 | 5 | **0** |
   | 추론 한 장 | 606 ms | **32 ms** (GTX 1060) |
   | 모델 | 83 MB + libtorch 4.3GB | 15 MB, 받을 것 없음 |

5. **기본 엔진 전환** - 쪽지가 `detector.onnx` 를 가리키므로 앱은 이미 새 모델로 돈다.
   실시간 길은 GPU 전처리(셰이더 2.5ms) + 추론 32ms 라 **한 번에 35ms 안쪽**, 목표(30ms)에 거의 닿았다.
   1060 에서 그렇고 4070 은 더 빠르다. `--use-trained` 로 옛 모델로 언제든 돌아간다.

   **libtorch 는 아직 지우지 않는다.** 찾기(추론)에는 더 이상 안 쓰지만 **앱 안에서 하는 학습**이
   그것을 쓴다. 지우려면 학습 쪽도 파이썬 길(`docs/ONNX-모델-학습.md`)로 옮기고, 그것을 libtorch 처럼
   눌렀을 때 받아 오게 감싸야 한다 - 그때 4.3GB 가 사라진다.

## 6. 위험과 대비

- **정확도가 떨어지면**: 채택하지 않는다. 문턱은 재현율 70%. 작은 봇을 놓치면 사진을 더 찍어 다시 학습한다.
- **DirectML 이 CUDA 보다 느리면**: NVIDIA 전용 CUDA EP 를 붙일 수 있다. 대신 패키지가 무겁다(수백 MB).
  0단계에서 DirectML 로 목표가 나오면 그냥 둔다 - 벤더를 안 가리는 것이 이 앱에는 더 값어치 있다.
- **출력 모양이 모델마다 다르면**: 디코더를 쪽지(클래스 수·입력 크기·출력 배치 순서)로 갈라 놓는다.
- **한 번에 갈아엎기**: 하지 않는다. 1단계의 인터페이스 덕분에 두 엔진이 같이 있고, 설정 하나로 오간다.

## 7. 지키는 것

- 인터페이스 + 구현 + 팩터리, 한국어 "왜" 주석, `--views`/`--vision` 검증(CLAUDE.md).
- **숫자로 정한다.** 빠르다·느리다가 아니라 ms 와 재현율 %로 말하고, 잰 값은 CLAUDE.md 표에 남긴다.
- 학습해 둔 모델을 못 쓰게 만들지 않는다. 언제든 옛 엔진으로 되돌아갈 수 있어야 한다.

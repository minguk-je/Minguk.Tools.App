# Minguk.Tools.Tests

입력 어댑터가 **실제로 OS 를 거쳐 살아 있는 창에 입력을 전달하는지** 확인하는 실행형 하네스다.
자기 소유의 WPF 창(TextBox · Button · ScrollViewer)을 띄우고 거기에 입력을 쏜 뒤 결과를 되읽는다.

단위 테스트 프레임워크를 쓰지 않는 이유는 검증 대상이 **실제 커서 위치와 실제 창의 입력 처리**이기
때문이다. 목으로는 확인할 수 없다.

## 실행

```
dotnet run --project Minguk.Tools.Tests -c Debug
```

경로를 바꿔 같은 검증을 돌린다. 경로마다 실제로 입력이 나가는지 따로 봐야 한다.

```
dotnet run --project Minguk.Tools.Tests -c Debug -- --backend=Interception
```

- 종료 코드 `0` 이 전체 통과, `1` 이 실패.
- 실행 중 **커서가 화면을 돌아다니고 창이 하나 뜬다.** 끝나면 커서를 원래 자리로 돌려놓는다.
- **실행하는 동안 마우스·키보드에서 손을 뗄 것.** 사람이 커서를 움직이면 검증이 그것과 싸운다.

## 검증 항목

| 항목 | 확인하는 것 |
|---|---|
| 어댑터 준비 | 고른 경로가 전송 가능하고 스캔코드를 넣을 수 있는지 |
| 경로 세 개 생성·정리 | SendInput · PostMessage · Interception 이 각각 만들어지고 Dispose 되는지 |
| 포커스 확보 | 대상 창이 키보드 포커스를 잡았는지 (이후 검증의 전제) |
| 키보드 문자 입력 | 대소문자(Shift) · 숫자 · Shift 문장부호가 **글자 사이 대기 0ms 연속 전송**에도 유실 없이 도착하는지 |
| Enter 키 | 스캔코드가 줄바꿈으로 도착하는지 |
| 절대 좌표 이동 | 붙어 있는 **모든 모니터**의 모서리·중앙에 정확히 착지하는지 (음수 좌표 포함) |
| 부드러운 이동 | 여러 단계를 거쳐도 목적지에 정확히 도착하는지 |
| 마우스 좌클릭 | 버튼의 Click 이벤트가 오르는지 |
| 휠 스크롤 | ScrollViewer 의 세로 오프셋이 실제로 움직이는지 |

## 알아 둘 것

- **전송은 백그라운드 스레드에서 해야 한다.** 보내는 스레드와 받는 창의 UI 스레드가 같으면
  연속 전송한 키가 유실된다. 실제 앱도 그렇게 돌므로 하네스도 같은 조건을 쓴다.
- **표시 영역 밖 좌표는 실패가 아니다.** 모니터를 어긋나게 배치하면 가상 화면 사각형 안에도
  어느 모니터에도 속하지 않는 빈 공간이 생긴다. 커서는 그 자리에 놓일 수 없어 Windows 가
  가장 가까운 화면으로 되돌리는데, 정상 동작이라 `표시 영역 밖(되튕김)` 으로만 표시하고 실패로 세지 않는다.

## 경로별로 다른 것 (실측)

같은 15개 지점을 두 경로로 재면 **모니터 이음매에 맞닿은 1px 열**에서 갈린다.

| 지점 | SendInput | Interception |
|---|---|---|
| 모니터4 우하 `(-1, 359)` | `(-2, 359)` 되튕김 | `(-1, 359)` 정확 |
| 모니터5 우하 `(-1, 1439)` | `(-2, 1439)` 되튕김 | `(-1, 1439)` 정확 |

`x = -1` 은 왼쪽 모니터의 오른쪽 끝 열이다. SendInput 은 정규화 좌표를 거치면서 이 열을
지정하지 못하지만(`--calibrate` 로 확인할 수 있다), Interception 은 드라이버로 바로 넣으므로 닿는다.
실제 UI 요소를 클릭하는 용도에서는 차이가 없다.

`모니터3 우하 (4479, 1438)` 는 두 경로 모두 되튕긴다. 이쪽은 좌표를 지정하는 문제가 아니라
그 자리가 어느 모니터에도 속하지 않는 빈 공간이라 커서를 놓을 수 없는 것이다.

## 자동 폴백 검증 (`--fallback`)

```
dotnet run --project Minguk.Tools.Tests -c Debug -- --fallback
```

Interception 드라이버가 **설치된** PC 에서는 폴백 분기가 영영 안 타므로,
`NativeLibrary.SetDllImportResolver` 로 `interception.dll` 로드를 의도적으로 실패시켜
드라이버가 없는 상황을 재현한다. 시스템 파일은 건드리지 않는다.

한 번 결정된 네이티브 함수 바인딩은 되돌릴 수 없어(성공적으로 로드된 뒤에는 리졸버가 다시
불리지 않는다) 본 검증과 같은 프로세스에서 돌릴 수 없다. 그래서 인자로 분리했다.
커서·창을 건드리지 않으므로 아무 때나 돌려도 된다.

## 정규화 규칙 실측 (`--calibrate`)

```
dotnet run --project Minguk.Tools.Tests -c Debug -- --calibrate
```

정규화 값(0~65535)을 그대로 넣어 커서가 어느 픽셀에 놓이는지 이분 탐색으로 잰다.
Windows 가 정규화 좌표를 픽셀로 되돌리는 규칙은 문서에 없으므로,
`VirtualScreen.Normalize` 를 건드릴 일이 생기면 추측 대신 이 출력으로 판단한다.

**반드시 마우스에서 손을 떼고 돌릴 것.** 커서를 수백 번 옮겨 가며 재는 도구라,
사람이 마우스를 잡고 있으면 측정값이 전부 무의미해진다(전 지점 "지정 불가" 로 나온다).

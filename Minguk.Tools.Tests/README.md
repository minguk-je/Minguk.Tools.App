# Minguk.Tools.Tests

입력 어댑터가 **실제로 OS 를 거쳐 살아 있는 창에 입력을 전달하는지** 확인하는 실행형 하네스다.
자기 소유의 WPF 창(TextBox · Button · ScrollViewer)을 띄우고 거기에 입력을 쏜 뒤 결과를 되읽는다.

단위 테스트 프레임워크를 쓰지 않는 이유는 검증 대상이 **실제 커서 위치와 실제 창의 입력 처리**이기
때문이다. 목으로는 확인할 수 없다.

## 실행

```
dotnet run --project Minguk.Tools.Tests -c Debug
```

경로를 바꿔 같은 검증을 돌린다. 경로마다 실제로 입력이 나가는지 따로 봐야 한다.

```
dotnet run --project Minguk.Tools.Tests -c Debug -- --backend=Interception
```

- 종료 코드 `0` 이 전체 통과, `1` 이 실패.
- 실행 중 **커서가 화면을 돌아다니고 창이 하나 뜬다.** 끝나면 커서를 원래 자리로 돌려놓는다.
- **실행하는 동안 마우스·키보드에서 손을 뗄 것.** 사람이 커서를 움직이면 검증이 그것과 싸운다.

## 검증 항목

| 항목 | 확인하는 것 |
|---|---|
| 어댑터 준비 | 고른 경로가 전송 가능하고 스캔코드를 넣을 수 있는지 |
| 경로 세 개 생성·정리 | SendInput · PostMessage · Interception 이 각각 만들어지고 Dispose 되는지 |
| 포커스 확보 | 대상 창이 키보드 포커스를 잡았는지 (이후 검증의 전제) |
| 키보드 문자 입력 | 대소문자(Shift) · 숫자 · Shift 문장부호가 **글자 사이 대기 0ms 연속 전송**에도 유실 없이 도착하는지 |
| Enter 키 | 스캔코드가 줄바꿈으로 도착하는지 |
| 절대 좌표 이동 | 붙어 있는 **모든 모니터**의 모서리·중앙에 정확히 착지하는지 (음수 좌표 포함) |
| 부드러운 이동 | 여러 단계를 거쳐도 목적지에 정확히 도착하는지 |
| 마우스 좌클릭 | 버튼의 Click 이벤트가 오르는지 |
| 휠 스크롤 | ScrollViewer 의 세로 오프셋이 실제로 움직이는지 |
| 한글 자판 매핑 | 음절이 두벌식 자리로 옳게 풀리는지 (겹받침·복합모음·된소리·호환 자모) |
| 한글 판별 | 완성형·호환 자모만 한글로 보는지 |
| 키보드 판별 | 키보드 Type/Subtype 으로 한/영 키가 무엇인지 알아내는지 |
| 한글 입력 | 한글과 영문을 섞어 쳐도 IME 를 알아서 맞추는지 |
| 계획 → 시퀀스 | 적어 둔 단계가 적은 순서 그대로 실행 시퀀스가 되는지 |
| 스크립트 왕복 | 글 → 계획 → 글 이 제자리로 돌아오는지 (따옴표·음수 좌표 포함) |
| 주석·빈 줄 | 세지 않고 넘어가는지, 따옴표 안의 `#` 은 글자로 두는지 |
| 틀린 줄 | 첫 오류에서 멈추지 않고 줄 번호와 함께 한 번에 모으는지 |
| 계획 저장·복구 | JSON 으로 나갔다 들어와도 같은 것인지, 종류를 이름으로 적는지 |
| 깨진 계획 | 설정이 망가졌을 때 터지지 않고 기본값으로 돌아가는지 |
| 계획 실행 | 계획으로 만든 시퀀스가 실제로 창에 닿는지 |
| 시퀀스 한 바퀴 | 담은 순서대로 나가고 끝까지 도는지 |
| 진행 보고 | 단계마다 `IProgress` 로 이름이 오는지 |
| 시퀀스 반복·취소 | 반복이 돌고, 취소한 뒤 더 나가지 않는지 |

## 알아 둘 것

- **전송은 백그라운드 스레드에서 해야 한다.** 보내는 스레드와 받는 창의 UI 스레드가 같으면
  연속 전송한 키가 유실된다. 실제 앱도 그렇게 돌므로 하네스도 같은 조건을 쓴다.
- **표시 영역 밖 좌표는 실패가 아니다.** 모니터를 어긋나게 배치하면 가상 화면 사각형 안에도
  어느 모니터에도 속하지 않는 빈 공간이 생긴다. 커서는 그 자리에 놓일 수 없어 Windows 가
  가장 가까운 화면으로 되돌리는데, 정상 동작이라 `표시 영역 밖(되튕김)` 으로만 표시하고 실패로 세지 않는다.

## 경로별 결과 (실측)

`[N/A ]` 는 실패가 아니다. 그 경로에 해당하지 않는 항목이다.

| 항목 | SendInput | Interception | PostMessage |
|---|---|---|---|
| 스캔코드 문자 입력 · Enter | PASS | PASS | N/A — 스캔코드를 넣지 못한다 |
| 가상 키 입력 | PASS | PASS | **PASS** |
| 시퀀스 (한 바퀴·반복·취소) | PASS | PASS | N/A — 스캔코드를 넣지 못한다 |
| 계획 (순서·저장·복구·깨진 것) | PASS | PASS | **PASS** |
| 스크립트 (왕복·주석·틀린 줄) | PASS | PASS | **PASS** |
| 계획 실행 | PASS | PASS | N/A — 스캔코드를 넣지 못한다 |
| 한글 입력 | PASS | PASS | N/A — 스캔코드를 넣지 못한다 |
| 절대 좌표 이동 · 부드러운 이동 | PASS | PASS | N/A — 진짜 커서를 안 움직인다 |
| 마우스 좌클릭 | PASS | PASS | N/A — 메시지는 도착하나 WPF 가 안 넘긴다 |
| 휠 스크롤 | PASS | PASS | **PASS** |

PostMessage 의 클릭은 `WM_LBUTTONDOWN` 이 창까지 **도착하는 것을 확인했다**(창에서 직접 센다).
WPF 는 창 하나가 전부라 자식 HWND 가 없고 마우스 입력을 실제 커서 위치로 판단해서, 부친 메시지가
어느 요소에도 닿지 않는다. 어댑터 문제가 아니라 대상이 WPF 라서 생기는 성질이고, 이 경로는
원래 Win32/WinForms 대상용이다. 같은 이유로 휠은 통한다 - `WM_MOUSEWHEEL` 은 lParam 이
화면 좌표라 WPF 가 그대로 쓴다.

가상 키 입력은 세 경로 모두 통한다. `PreviewInputRouter` 가 실제로 쓰는 길이 이쪽이다.

계획(`SequencePlan`)과 스크립트(`SequenceScript`)를 다루는 항목들은 경로와 무관하다 - 적어 둔 것을 읽고 쓰는 순수 계산이라
어느 경로로 돌려도 같아야 하고, 세 경로 모두에서 돌려 그것을 확인한다.
"계획 실행" 만 실제로 키를 보내므로 경로를 탄다.

## 커서 좌표에서 경로별로 다른 것 (실측)

같은 15개 지점을 두 경로로 재면 **모니터 이음매에 맞닿은 1px 열**에서 갈린다.

| 지점 | SendInput | Interception |
|---|---|---|
| 모니터4 우하 `(-1, 359)` | `(-2, 359)` 되튕김 | `(-1, 359)` 정확 |
| 모니터5 우하 `(-1, 1439)` | `(-2, 1439)` 되튕김 | `(-1, 1439)` 정확 |

`x = -1` 은 왼쪽 모니터의 오른쪽 끝 열이다. SendInput 은 정규화 좌표를 거치면서 이 열을
지정하지 못하지만(`--calibrate` 로 확인할 수 있다), Interception 은 드라이버로 바로 넣으므로 닿는다.
실제 UI 요소를 클릭하는 용도에서는 차이가 없다.

`모니터3 우하 (4479, 1438)` 는 두 경로 모두 되튕긴다. 이쪽은 좌표를 지정하는 문제가 아니라
그 자리가 어느 모니터에도 속하지 않는 빈 공간이라 커서를 놓을 수 없는 것이다.

## 한글 검증은 세 층이다

| 층 | IME 가 필요한가 | 무엇을 잡는가 |
|---|---|---|
| 자판 매핑 · 한글 판별 | 필요 없음 | 음절 분해 표가 틀어졌는지. 순수 계산이라 늘 돈다 |
| 키보드 판별 | 필요 없음 | 이 PC 의 한/영 키가 무엇인지 |
| 한글 입력 | **필요함** | 실제로 한글이 찍히는지, IME 전환이 되는지 |

**이 하네스로 못 잡는 것이 하나 있다.** 대상이 WPF 창이라 최상위 창과 포커스 창이 같다.
Win32·WinForms 처럼 컨트롤마다 HWND 가 따로인 대상에서만 드러나는 문제가 있었고
(IME 상태를 최상위 창에 물어 늘 영문으로 읽던 것), 그건 메모장으로 확인해서 잡았다.
한글 관련을 고칠 때는 메모장 같은 Win32 대상으로도 한 번 쳐 볼 것.

마지막 층은 **입력 언어가 한국어일 때만** 돈다. 아니면 어떤 키를 보내도 한글이 나오지 않으므로
`[N/A ]` 로 건너뛰고 이유를 적는다. 앞의 두 층이 따로 있는 이유가 이것이다 - IME 가 없는
환경에서도 분해 표가 맞는지는 잡을 수 있어야 한다.

조합 중인 마지막 음절은 확정 전까지 IME 가 들고 있어서, 다 친 뒤 Enter 로 확정하고 읽는다.

## 자동 폴백 검증 (`--fallback`)

```
dotnet run --project Minguk.Tools.Tests -c Debug -- --fallback
```

Interception 드라이버가 **설치된** PC 에서는 폴백 분기가 영영 안 타므로,
`NativeLibrary.SetDllImportResolver` 로 `interception.dll` 로드를 의도적으로 실패시켜
드라이버가 없는 상황을 재현한다. 시스템 파일은 건드리지 않는다.

한 번 결정된 네이티브 함수 바인딩은 되돌릴 수 없어(성공적으로 로드된 뒤에는 리졸버가 다시
불리지 않는다) 본 검증과 같은 프로세스에서 돌릴 수 없다. 그래서 인자로 분리했다.
커서·창을 건드리지 않으므로 아무 때나 돌려도 된다.

## 화면 생성 확인 (`--views`)

```
dotnet run --project Minguk.Tools.Tests -c Debug -- --views
```

XAML 은 빌드를 통과하고 런타임에만 터진다 - 리소스 경로가 틀렸거나, 바인딩 대상이 없거나,
아이콘 이름이 없거나. 빌드 오류 0 을 확인했다고 화면이 뜬다는 뜻이 아니다.

잡는 것: XAML 파싱, 리소스 사전 해석, `ViewModelSource` 로 ViewModel 생성,
메뉴의 `CLASS_NM` 이 실제 타입을 가리키는지, 아이콘이 잡히는지.
그리고 **고른 경로가 못 보내는 단계가 있을 때 화면이 그것을 말하는지** —
PostMessage 로 두면 글자·Enter·한/영 이 통째로 빠지는데, 알려 주지 않으면
"순서" 가 비고 실행해도 아무 일이 없는 이유를 알 수 없다.

`CLASS_NM` 은 문자열이라 오타가 나도 빌드는 통과한다. `MainViewLocator` 가 그 이름으로
DI 에서 뷰를 꺼내므로, 틀리면 **메뉴는 보이는데 탭이 비어서 열린다**. 그 실수를 여기서 잡는다.

못 잡는 것: 부모(MainViewModel)가 주입되어야 도는 초기화 단계.
문서 탭 안에서만 일어나므로 그 뒤는 앱에서 눈으로 봐야 한다.

**AvalonEdit 편집기 안의 글은 UI 자동화로 읽거나 쓸 수 없다.** 바깥에서 스크립트를 고치려면
좌표로 클릭해 포커스를 준 뒤 키를 보내는 수밖에 없다. 버튼(담기·처음으로)은 UIAutomation 으로
눌리므로, 스크립트가 바뀌는지는 "순서" 칸으로 본다.

창을 UIAutomation 으로 훑을 때 **요소가 하나도 안 잡히면 앱이 죽은 것이 아니라 트리가 무너진
것일 수 있다.** 실제로 AvalonEdit 을 그냥 얹었을 때 창 전체가 비어 보였다
(버튼 37개 → 0개). `Markup/ScriptEditor` 가 그것을 막고 있으니, 비슷한 증상을 만나면
새로 얹은 컨트롤의 자동화 피어부터 의심할 것.

또 하나: `RootElement` 의 자식을 프로세스 ID 로 찾으면 **뜨는 도중의 스플래시나 숨은 창이
먼저 잡힐 수 있다.** `AutomationElement.FromHandle(proc.MainWindowHandle)` 로 집는 편이 낫다.

## 정규화 규칙 실측 (`--calibrate`)

```
dotnet run --project Minguk.Tools.Tests -c Debug -- --calibrate
```

정규화 값(0~65535)을 그대로 넣어 커서가 어느 픽셀에 놓이는지 이분 탐색으로 잰다.
Windows 가 정규화 좌표를 픽셀로 되돌리는 규칙은 문서에 없으므로,
`VirtualScreen.Normalize` 를 건드릴 일이 생기면 추측 대신 이 출력으로 판단한다.

**반드시 마우스에서 손을 떼고 돌릴 것.** 커서를 수백 번 옮겨 가며 재는 도구라,
사람이 마우스를 잡고 있으면 측정값이 전부 무의미해진다(전 지점 "지정 불가" 로 나온다).
